如果说选择机场和安装客户端决定了你的网络工具「能不能连上」，那么**分流规则（Routing Rules）**决定的则是这套工具「好不好用、省不省流量、会不会触发封号」。

现实中最常见的三种用网崩溃场景，其实全部源于规则缺位或顺序错乱：第一种，长期开着 `Global` 全局模式，导致淘宝加载图片转圈、企业微信文件传输龟速、百度网盘把月付 150GB 的专线流量三天跑光；第二种，默认规则把延迟只有 25 毫秒的香港节点设成了唯一主力出口，结果网页版 ChatGPT、Claude、Gemini 和 TikTok 轮番报错拒绝服务；第三种，明明照着网上教程粘了几十行规则进去，改完刷新网页却依然毫无变化——因为既没理解规则自上而下的「短路机制」，也没有清理浏览器残留的 QUIC 长连接。

本文将从规则语法内核、匹配优先级与 `no-resolve` 机制讲起，对比三类工作模式与现代 `.mrs` / `.srs` 二进制规则集，并最终落出一套覆盖 **国内直连 + 国际通用 + AI 三巨头排港隔离 + 流媒体精细分流** 的完整工程规则结构。

## 一、核心规则语法与匹配优先级：自上而下短路原则与 `no-resolve`

在 [Mihomo](/clients/mihomo/)（原 Clash.Meta）与 [sing-box](/clients/sing-box/) 的规则路由引擎中，不管你的规则列表有 20 行还是 20 万行，引擎在调度每一条新建网络连接时，都只遵循一条铁打不动的执行逻辑：**自上而下短路原则（First-Match Short-Circuit）**。

具体而言：当一条请求进入内核，引擎从 `rules` 列表的第 1 行开始逐行往下核对。**只要命中了某一条规则，内核立刻终止后续所有规则的匹配扫描**，直接把数据包交给该规则末尾指定的出站目标（例如 `DIRECT`、`REJECT` 或某个策略组）；只有当前一条未命中时，才会继续往下检测下一行，直到触达最底部的兜底规则（`MATCH`）。

理解了「短路原则」，就能瞬间明白为什么**规则排错顺序会导致整套配置瘫痪**：如果你不小心把宽泛的 `GEOSITE,cn,DIRECT` 或者兜底的 `MATCH,🚀 节点选择` 放到了第 1 行，那么写在它下面的所有精密的 OpenAI、Claude、内网直连规则全都会变成永远不会执行的死代码。

### 1. 八大常用规则类型精度、性能与工程排位对照表

| 规则关键字 | 匹配对象与作用逻辑 | 工程性能开销 | 推荐排位层级 | 典型写法示例（不含多余注释） |
| :--- | :--- | :--- | :--- | :--- |
| **`DOMAIN`** | **精确完整域名匹配**，仅当请求域名一字不差完全一致时命中 | 极低（哈希表 O(1) 查找） | **第一梯队（最顶层）** | `DOMAIN,api.openai.com,🤖 AI-OpenAI` |
| **`DOMAIN-SUFFIX`** | **域名后缀匹配**，命中主域名及其所有子域名（如匹配 `openai.com` 即同时覆盖 `chat.openai.com`） | 极低（后缀树匹配） | **第一梯队（高优先级主力）** | `DOMAIN-SUFFIX,claude.ai,🤖 AI-Claude` |
| **`DOMAIN-KEYWORD`** | **域名关键词子串匹配**，只要域名任意位置包含该词即命中（容易误伤无关域名，慎用） | 中等（逐条字符串扫描） | **仅作补充例外（尽量少用）** | `DOMAIN-KEYWORD,openai,🤖 AI-OpenAI` |
| **`DOMAIN-REGEX`** | **正则表达式匹配域名**，适合处理编号规律极强的 CDN 或特定泛域名集群 | 较高 | **按需精准置顶** | `DOMAIN-REGEX,^googlevideo\.com$,🎬 YouTube` |
| **`RULE-SET`** | **引用外部托管或本地规则集**（推荐使用 `.mrs` / `.srs` 二进制规则包，动辄承载数万条域名或 IP） | 极低（编译后前缀树） | **第二梯队（主体分流层）** | `RULE-SET,ai_bundle,🤖 AI-OpenAI` |
| **`GEOSITE`** | **内核内置或加载的分类域名库**（如 `cn`、`private`、`openai`、`netflix`、`geolocation-!cn`） | 低（依赖 `geosite.dat`） | **第二梯队（若已用全套 `mrs` 可替代）** | `GEOSITE,cn,DIRECT` |
| **`IP-CIDR` / `IP-CIDR6`** | **IPv4 或 IPv6 网段匹配**，用于兜底纯 IP 请求与局域网私网放行 | 极低（基数树位运算） | **第三梯队（兜底前置段，需带 `no-resolve`）** | `IP-CIDR,192.168.0.0/16,DIRECT,no-resolve` |
| **`GEOIP`** | **IP 地理位置归属库匹配**（最常见用于 `GEOIP,CN,DIRECT` 国内 IP 直连兜底） | 低（基于 MaxMind mmdb / mrs） | **第三梯队（紧贴 `MATCH` 之前，必须带 `no-resolve`）** | `GEOIP,CN,DIRECT,no-resolve` |

此外，在桌面端或客户端侧（非网关旁路由）还可以利用 **`PROCESS-NAME`** 按本地软件进程名强制分流——例如把 P2P 下载软件（如 `qBittorrent` 或国内网盘客户端）直接置顶设为 `PROCESS-NAME,qbittorrent.exe,DIRECT`，不仅避免 P2P 高并发触发机场后台滥用封号，还能防止上传流量把套餐额度瞬间抽干。

### 2. 深入理解 `no-resolve` 参数：为什么 IP 规则漏加它会拖慢全网？

在阅读成熟规则模板时，几乎所有 `IP-CIDR` 与 `GEOIP` 规则尾部都附带着一个 `no-resolve` 参数。对于很多初学者来说，这是最容易被顺手删掉却后果严重的关键字。

设想这样一个真实请求流：你在浏览器访问一个尚未被前面域名规则拦截的冷门国外网站，请求以**域名形式**进入规则树。当它一路向下扫描来到 `GEOIP,CN,DIRECT` 这一行时：

- **如果没有加 `no-resolve`**：Mihomo 为了搞清楚这个冷门域名究竟是不是中国的 IP，会**强行暂停当前转发流程**，立刻调用本地 DNS 去解析这个域名的真实 A 记录。如果本地网络刚好被污染或等待 DNS 超时，整个请求会平白无故卡住几百毫秒甚至数秒；更糟糕的是，在 `redir-host` 模式下这还会导致原本应当交由海外节点去解析的境外域名提前泄露给本地 DNS（排查方法参见 [DNS 污染与泄漏专项排障](/troubleshooting/dns/)）。
- **加上 `no-resolve` 之后**：内核看到这是一条还未解析成纯 IP 的域名请求，便会直接跳过 `GEOIP,CN` 这一行，继续向下落入末尾的 `MATCH,🚀 节点选择`，直接把域名交给海外代理节点去远端解析并拉取网页，实现零延迟阻塞且零本地 DNS 泄漏。而真正本身就以纯 IP 发起的直连请求（例如局域网访问路由后台或微信、游戏直连服务器 IP），则会毫无阻碍地命中 `IP-CIDR` 或 `GEOIP,CN` 走直连。

## 二、三类分流模式对比与现代 `.mrs` / `.srs` 二进制规则集演进

理解了单条规则怎么匹配，接着就要从宏观上选定客户端的运行模式与规则集载体格式。

### 1. `Rule` vs `Global` vs `Direct` 三类模式，以及白名单/黑名单分流哲学

在几乎所有代理客户端的顶栏，都能看到三个核心运行模式开关：

1. **`Rule`（规则模式）**：日常唯一推荐的常驻模式。所有流量严格进入上述「自上而下短路规则树」接受调度，既能保障国内站点全速直连不耗套餐流量，又能让海外资料、AI 与流媒体精准走各自对应的优化节点。
2. **`Global`（全局模式）**：直接绕过精细的 `rules` 列表（部分内核仅保留最基础的回环与私有地址直连防死锁），将几乎所有外部连接强行塞进名为 `GLOBAL` 的总策略组所指派的那一个节点。**用途边界**：只用来在排障时验证「某个打不开的网站究竟是节点挂了，还是我的规则写漏了」。排查完毕必须立刻切回 `Rule`。
3. **`Direct`（直连模式）**：彻底跳过所有远程代理节点，所有流量直接走本地网卡。用于测试宽带原生故障或进入特殊内网办公。

在 `Rule` 模式内部，长期以来存在「白名单派」与「黑名单派」两条分流路线：
- **白名单思路（主流推荐）**：列出局域网、国内域名、国内 IP 全部 `DIRECT`，最底部 `MATCH` 全部交给 `🚀 节点选择`。优点是遇到任何新上线或小众的海外科研、开源文档网站无需手动补规则即可秒开；缺点是极少数刚上线还没来得及收录进国内规则库的本土小站可能会走一次代理。
- **黑名单思路**：列出需要加速访问的海外服务走代理，最底部 `MATCH` 设为 `DIRECT`。优点是国内流量绝对零误判、最省机场流量；缺点是维护心智极高，国外网站哪怕漏掉一个静态资源 CDN 域名就会网页排版错乱，一般仅在极小容量流量包或特定办公隔离场景下使用。

### 2. `.mrs` 与 `.srs` 现代二进制规则集为什么能取代传统文本？

在早期的 Clash 配置里，规则要么直接塞在主 YAML 里，要么通过 `rule-providers` 拉取纯文本 `.yaml` 或 `.list` 列表；地理数据库则依靠体积庞大的 `GeoSite.dat` 和 `Country.mmdb`。随着国内外域名列表膨胀到数十万条，传统文本和全量 `.dat` 数据库暴露出三大硬伤：软路由加载内存暴涨、每次重启或切换配置耗时数秒解析、远端同步带宽消耗大。

现代双雄内核各自给出了高度一致的二进制演进方案——**Mihomo 的 `.mrs`（Mihomo Rule-Set）** 与 **`sing-box` 的 `.srs`（sing-box Rule-Set）**：

| 对比维度 | 传统文本规则（`.yaml` / `.list`） | 传统全量地理库（`.dat` / `.mmdb`） | 现代二进制规则集（`.mrs` / `.srs`） |
| :--- | :--- | :--- | :--- |
| **底层存储结构** | 纯文本明文列表，含大量前缀关键字重复 | 打包了全球所有国家和地区分类的巨型单文件（通常 10MB 以上） | **预编译的紧凑二进制前缀树 / 基数树**，按需拆分单类目独立文件（常仅几十 KB） |
| **内存与闪存占用** | 极高，文本解析期间内存翻倍 | 高，即使你只需要 `cn` 和 `openai`，也得把全球所有冷门地区整包载入低闪存路由器 | **极低**，可按需只挂载 `cn`、`private`、`openai` 等少数模块，软路由毫无压力 |
| **冷启动与匹配耗时** | 每次更新都要重新编译匹配树，较慢 | 加载全库耗时长 | **毫秒级零解析加载**，且内部路由查找时间复杂度最优 |
| **内核兼容性要求** | 全版本兼容 | 全版本兼容 | `.mrs` 需较新 [Mihomo](/clients/mihomo/) 内核（如 [Clash Verge Rev](/clients/clash-verge-rev/)、`FlClash`、`OpenClash` 新核、`Nikki`）；`.srs` 需 [sing-box](/clients/sing-box/) `1.8.0+`（如 `Hiddify`、`Karing`、`HomeProxy`、`SFA/SFI/SFM`），订阅格式转换可见 [订阅与规则格式指南](/guides/subscription/) |

## 三、标准工程规则架构实战：国内直连 + 国际通用 + AI 排港 + 流媒体分区分流

下面结合站内品牌实测数据库中的客观特征，构建一套可直接投入日常主力使用的标准工程分流架构。为什么不能把所有海外流量都扔进一个组？站内的两份真实样本早已给出铁证：

- **AI 锁区排除香港的实测依据**：在 [光速云](/brands/guangsuyun/) 2026-08-19 归档的三网 62/70 节点 MiaoKo 实测截图中，20 个 [香港节点](/routes/hong-kong/) 虽然延迟低至 20–31 毫秒，但 [ChatGPT](/ai-media/chatgpt/)（OpenAI）解锁几乎全部显示「仅 APP(HK)」而网页端受限，Gemini 更是全线失败；相反，[日本节点](/routes/japan/) 与美国节点网页端 OpenAI 表现稳健，新加坡节点则在当时同时解锁了 Gemini 与大量服务。同时如 [Claude 访问与风控指南](/ai-media/claude/) 所述，Claude 必须绑定手动锁定的非香港低风险节点。
- **流媒体分化与防送中实测依据**：在 [光速云](/brands/guangsuyun/) 08-19 与 [灵动云](/brands/lingdongyun/) 2026-07 实测样本中，均观测到部分新加坡与台湾节点出现 **[YouTube 送中（CN）](/ai-media/youtube/)**（即 IP 被 Google 误判为中国大陆地区导致无广告或功能受限），以及台湾广播 IP 在 **[Netflix 解锁](/ai-media/netflix/)** 上被识别成英国（GB）或西班牙（ES）片库的现象；而 **TikTok** 已退出香港市场，使用香港节点必黑屏；至于台湾**巴哈姆特动画疯（Bahamut）**与日本 **ABEMA TV**，对本土 IP 或特定解锁出口有着极高要求（详见 [Disney+、动画疯与 TikTok 解锁专题](/ai-media/streaming/)）。

### 1. 策略组职责分层图谱

为了彻底解决「快而不全、全而不快」的矛盾，标准的工程架构将全部策略出口拆解为七个职责清晰的分组（具体策略组 YAML 参数与正则排港写法见 [Clash / Mihomo 配置文件教程](/guides/clash-config/)）：

1. **`🚀 节点选择`（日常通用国际出口）**：默认主力，可放心地选择 [香港低延迟节点](/routes/hong-kong/)（20–30ms）或 [日本节点](/routes/japan/)、新加坡高速节点，承载 Google 搜索、GitHub、开发者文档、Docker 镜像与普通外网浏览。
2. **`🤖 AI-OpenAI与Claude`（非港锁定 `select` 组）**：通过正则强制排除香港、台湾与信息节点（同时过滤 [高倍率节点](/routes/multiplier/)），人工锁定 1 个稳定日本、新加坡或美国节点（禁用自动测速跳线）。
3. **`✨ AI-Gemini`（区域特化 `select` 组）**：根据当前机场实测表现，优先锁定明确绿标解锁的新加坡或美国原生定位节点，且配套处理同一会话下的 Google 账号域一致性（详见 [Gemini 节点分化实况](/ai-media/gemini/)）。
4. **`🎬 流媒体-Netflix与Disney`（高带宽解锁 `select` 组）**：方便根据片库字幕需求在港、台、日、新之间手动切换原生全解锁高带宽节点，避免自动切到只能看自制剧的机房 IP（参见 [Netflix 分区实况](/ai-media/netflix/)）。
5. **`📺 流媒体-YouTube防送中`（独立可控 `select` 组）**：专门避开在测速表中出现过「送中(CN)」的新加坡/台湾广播节点，稳定指向未送中的日本、香港或美国大带宽节点（参见 [YouTube 送中排查](/ai-media/youtube/)）。
6. **`⛩️ 动漫专属-动画疯与ABEMA`（区域强制指向组）**：分别拆分台湾原生组（供巴哈姆特动画疯）与日本原生解锁组（供 ABEMA TV），互不干扰（参见 [流媒体解锁专题](/ai-media/streaming/)）。
7. **`🎵 TikTok专属`（非港锁定 `select` 组）**：严格排除香港节点，指派日本、新加坡、美国或英国支持地区。

### 3. 联动深度案例：为什么单配域名有时依然报错？

上述工程结构已经覆盖了绝大部分日常场景，但在实际落地时仍有两类隐藏细节需要结合 [AI 与流媒体 GeoIP 分流实战规则](/guides/articles/ai-streaming-geoip-routing/) 同步留意：

- **Google 主账号与 Gemini 的地域上下文联动**：当你的主力浏览器登录着 Google 账号，如果 `google.com` 或 `accounts.google.com` 走了香港节点、而 `gemini.google.com` 走了新加坡节点，Google 服务端风控有概率因为同一会话在极短时间内横跨两个地域接口而拒绝 Gemini 访问。一旦遇到此类连带报错，可以在使用 Gemini 期间把日常主策略组或整个 Google 域名集群暂时同步切往同一非香港国家节点。
- **Disney+ 与流媒体静态/CDN 资源域关联**：流媒体平台往往存在主网页域与视频切片流域分离的情况（例如 Netflix 的 `nflxvideo.net`、Disney+ 的 `bamgrid.com` 与 `dssott.com`）。如果规则漏掉了视频流 CDN 域，就会出现片单封面能刷出来、一点播放按钮立刻转圈报错的假象，甚至消耗高倍率默认组流量。

## 四、常见国产软件、开发工具与网盘误入代理的高耗流纠偏案例

哪怕写好了 AI 与流媒体规则，现实中最容易把用户月付套餐或高价不限时包「一夜烧穿」的元凶，往往不是海外网站，而是**未命中国内直连规则的国产大流量软件、网盘客户端与本地开发工具**。一旦这类大吞吐流量误走代理，再叠加上部分机场线路的 `2x`–`5x` [流量倍率系数](/routes/multiplier/)，往往一晚就能白白扣光几十甚至上百 GB 配额（尤其对于购买了 [光速云](/brands/guangsuyun/) `¥147/247GB` 等 [不限时一次性流量包](/pricing/non-expiring/) 的用户，更是不可挽回的纯损耗）。

### 1. 五类高发误入代理场景与纠偏对照表

| 误入场景分类 | 典型软件与请求特征 | 误走代理的真实后果（含倍率放大） | 精准规则纠偏方法（置于第 1 层最高优先级） |
| :--- | :--- | :--- | :--- |
| **国产网盘与云同步** | 百度网盘、阿里云盘、夸克网盘、WPS/飞书大附件传输 | 上传下载双向计费；若误连 `3x` 节点传 20GB 素材，后台直接扣除 `60GB` 配额且速度大幅缩水 | 用 `PROCESS-NAME` 强制直连网盘主程序，并将国内对象存储 CDN 后缀显式列入前置 `DIRECT` |
| **国内开源镜像源** | `npmmirror`、清华/阿里 PyPI 镜像、Docker 国内加速、Gitee | 依赖包下载本来就在国内节点，绕道香港或美国节点反而降至几百 KB/s 并白烧几十 GB 镜像流量 | 将国内镜像域名后缀置顶 `DIRECT`，仅保留 `github.com` 与海外原始源走 `🚀 节点选择` |
| **游戏更新与 P2P 挂种** | Steam/Epic 游戏大更新、系统大版本升级、`qBittorrent` / 迅雷 | 动辄 50–100GB 下载包与整夜做种上传瞬间打爆小包套餐，P2P 高并发还可能触发机场审计限速 | 将 BT/PT 客户端进程名直接置顶 `DIRECT`，系统大更新下载期间核查 `MATCH` 未误命中高倍率组 |
| **国产音视频与直播** | 腾讯会议、钉钉/飞书音视频会议、B 站/虎牙直播推送 | 高并发 UDP 音视频流绕行跨国节点造成延迟飙升、画面卡顿，同时持续消耗代理流量 | 通过完整 `cn_domain` 与会议进程直连双保险锁定 `DIRECT`，确保实时媒体包不进代理隧道 |
| **开发容器与内网** | `Docker`、`WSL2`、公司零信任 VPN、内网 `GitLab` / ERP | `fake-ip` 假地址或代理规则拦截私有域导致镜像拉取失败、内网系统超时断连 | 把公司内部域名与私有网段置顶 `DIRECT`（带 `no-resolve`），并在 [TUN 模式](/guides/tun/) 补齐 `fake-ip-filter` |

### 2. 真实纠偏规则模板与适用边界

需要注意，只有支持通用订阅导出的机场（如 [光速云](/brands/guangsuyun/)、[一翻云](/brands/yifan/)、[梯子云](/brands/tiziyun/)、[可信云](/brands/kexin/) 等）才允许你在 [Clash Verge Rev](/clients/clash-verge-rev/) 中注入以下自定义防偷跑规则；如果是 [飞猫云](/brands/feimao/)、[隐形人](/brands/yinxingren/) 等纯专属客户端品牌，则无法手动修改内核级规则列表（参见 [专属客户端 vs 通用订阅对照](/compare/dedicated-client-vs-universal-sub/)）。针对通用订阅用户，可直接在覆写 `prepend-rules` 顶部加入以下纠偏片段：

```yaml
# 防高倍率偷跑与国内开发/网盘纠偏（置顶插入第 1 层）
prepend-rules:
  # 1. 国内常见网盘、云盘与高吞吐传输进程直连（仅桌面端进程匹配生效）
  - PROCESS-NAME,baidunetdisk.exe,DIRECT
  - PROCESS-NAME,aDrive.exe,DIRECT
  - PROCESS-NAME,QuarkCloudDrive.exe,DIRECT
  - PROCESS-NAME,qbittorrent.exe,DIRECT
  - PROCESS-NAME,Thunder.exe,DIRECT

  # 2. 国内开发镜像源与代码托管直连（与海外 GitHub 明确分离）
  - DOMAIN-SUFFIX,npmmirror.com,DIRECT
  - DOMAIN-SUFFIX,tuna.tsinghua.edu.cn,DIRECT
  - DOMAIN-SUFFIX,mirrors.aliyun.com,DIRECT
  - DOMAIN-SUFFIX,gitee.com,DIRECT

  # 3. 常见国内网盘传输与会议服务核心域补充直连兜底
  - DOMAIN-SUFFIX,baidupcs.com,DIRECT
  - DOMAIN-SUFFIX,aliyundrive.com,DIRECT
  - DOMAIN-SUFFIX,meeting.tencent.com,DIRECT
```

最后再配合策略组正则把 `2x`、`3x`、`5x` 高倍率节点从主力自动组剔除，就能彻底堵住「挂着代理传网盘或拉依赖却莫名耗光套餐」的隐藏漏洞。

## 五、规则修改后的生效铁律：清理长连接、处理 QUIC 与日志验证

几乎每一个刚学写分流规则的用户都踩过同一个坑：**明明把规则写得完美无缺并保存生效了，刷新浏览器打开 ChatGPT 或 Netflix 却发现依然报错，甚至连接日志里显示它还在走老的香港节点**。

这并不是分流规则没起作用，而是现代网络协议的**长连接复用（Keep-Alive 与 HTTP/3 QUIC）**机制在作祟：

1. **TCP/TLS 与 HTTP/3 长连接不会自动断开**：代理客户端里的 `rules` 规则只在**建立新连接的那一瞬间**执行一次匹配判断。只要你刚才打开网页时已经通过香港节点建好了一条长连接，哪怕你一秒后把规则改成了日本节点，浏览器接下来的几十秒甚至几分钟内依然会沿着那条还没关闭的旧隧道继续发数据包。
2. **UDP 443（QUIC）在部分代理环境下的绕过与卡顿**：现代 Chrome、Edge 与手机 App 默认优先通过 UDP 443 端口尝试 HTTP/3（QUIC）握手。部分机场节点对 UDP 转发支持不佳，或旧 QUIC 会话死死咬住旧路由不放。这也是为什么上文工程模板中预留了针对特定视频流或域名的 `REJECT-DROP` 示例——拒绝 UDP 443 后，浏览器会在毫秒内自动降级回走标准且稳定的 TCP TLS 连接，规则接管立刻变得顺滑精准。

**每次调整完分流规则后，请严格执行以下四步验证动作**：

1. **断开客户端全部活跃连接**：在 `Clash Verge Rev`、FlClash 或 `Shadowrocket` 的连接（Connections / 请求日志）管理页面，点击「关闭全部连接（Close All Connections）」按钮，强行掐断所有历史残余会话。
2. **刷新本地浏览器测试环境**：新开一个浏览器无痕隐私窗口（Incognito Mode），避开原窗口里已经打上地区拦截标记的 Cookie 与 LocalStorage 缓存，重新访问目标站点（如 `chatgpt.com` 或 `claude.ai`）。
3. **打开实时连接面板核对命中行**：回到客户端「连接」页面，在搜索框内键入目标域名关键词（如 `anthropic`、`openai`、`googlevideo`、`netflix`），重点观察每一条活跃连接右侧显示的**命中规则（Rule）**和**实际链路（Chains）**：
   - 若命中规则显示为 `DOMAIN-SUFFIX(claude.ai)` 且链路末端的节点名称为你指定的日本或美国节点，说明规则 100% 精准接管；
   - 若命中规则显示为 `MATCH` 且节点跳去了香港，说明该请求使用了某个未列入规则的辅助子域名（例如登录验证接口的新域名），把日志中显示的新域名直接补进第 2 层对应分组即可彻底堵住漏洞。
4. **验证国内业务是否零耗流**：最后打开一个国内常见视频站或网盘，确认连接面板中对应请求的链路显示为 `DIRECT`，且不再经过任何机场节点，整套分流工程即正式验收完成。

如果在使用高配规则时遇到部分命令行工具（如 `git`、`curl`、`Python`、`Claude CLI`）或 UWP 应用完全不理会系统代理分流规则的情况，请继续阅读 [TUN 虚拟网卡模式原理解析](/guides/tun/)，让底层虚拟网卡接管与这套规则树形成完整闭环。
