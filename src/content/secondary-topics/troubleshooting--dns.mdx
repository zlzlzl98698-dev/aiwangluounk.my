在桌面与移动端代理故障中，最令人困惑的一类现象往往不是“完全连不上”，而是看似已经连接成功、节点延迟也显示绿色，却接连出现各种违反直觉的网络异常：比如刚退出客户端整个电脑就打不开任何国内网站，打开百度和 B 站转圈十秒才出图，家里局域网 NAS 或公司内网突然失联，或者明明连着新加坡节点，ChatGPT 和 Gemini 却依然频繁提示地区受限。

这些看似毫不相干的症状，底层大多指向同一个核心环节——**域名系统（DNS）解析链路失控**。当代理客户端、操作系统缓存、浏览器自带加密 DNS、移动系统私人 DNS 以及国内外分流规则互相抢夺解析权时，哪怕你的节点线路本身毫无故障，数据包也会被送往错误的 IP 甚至彻底丢进本地黑洞。本文将围绕 DNS 污染与泄露机理、Fake-IP 缓存残留清理、DoH 与 DoT 冲突解除、国内外分流纠偏以及 AI 场景防泄露核验五个维度，提供一套可逆、无损的深度排障指南。

> **排障前安全守则**：修改任何客户端配置文件或网卡 DNS 参数前，务必先备份当前可用的配置目录（如 `profiles` 文件夹），并记录或截图保留本机有线/无线网卡原先的 IPv4 与 IPv6 DNS 状态（普通家庭宽带一般为自动获取 DHCP；企业办公网若有手动静态 DNS 切勿直接抹除）。切忌运行来路不明、会清空全部网络拨号与虚拟网桥配置的破坏性重置脚本。

## 一、底层机理先看清：污染、泄露、`Fake-IP` 与 `Redir-Host` 如何打架

要精准定位 DNS 故障，必须先分清代理环境下的域名解析究竟经过了哪几道关卡。在直连上网时，系统只需向本地路由器或运营商 DNS 询问一次 IP 即可建连；而在启用规则分流（Rule 模式）的代理客户端（如基于 `Mihomo` 内核的 [Clash Verge Rev](/clients/clash-verge-rev/)、FlClash，或基于 `sing-box` 内核的 [v2rayN](/clients/v2rayn/)、Hiddify、Karing）后，DNS 不再只是“把域名变成 IP”，它同时承担着**决定后续流量走直连还是走代理**的哨兵角色。

### 1. DNS 污染 vs DNS 泄漏（DNS Leak）：两种截然相反的故障

日常讨论中，很多用户容易把“DNS 污染”和“DNS 泄漏”混为一谈，实际上两者的发生方向和危害完全不同：

- **DNS 污染（DNS Poisoning）**：通常发生在**没有正确走加密通道**的明文 UDP 53 端口查询上。当你试图解析境外域名时，途中网络设备会抢先伪造并返回一个错误的、无法连通的 IP 地址（或本地回环地址）。表现为网站完全打不开、TLS 证书报错或者被导向毫无关联的服务器。
- **DNS 泄漏（DNS Leak）**：指你的网页数据流明明已经通过代理节点的加密隧道发出去了，但发起连接前的那一次“域名查询请求”却因为客户端未接管、规则漏配、浏览器开启独立 DoH 或 IPv6 旁路直连，**明文或直接发给了本地国内运营商 DNS（甚至发给了与代理节点国家不匹配的其它区域 DNS）**。DNS 泄漏不仅会暴露你的访问意图清单，在访问高风控服务（如 ChatGPT、Claude、Gemini 或流媒体平台）时，还会因为解析出的边缘节点归属与实际出口 IP 地理位址错位，引发访问降级、无限人机验证甚至直接拒绝服务。

### 2. `Fake-IP` 与 `Redir-Host` 的机制冲突边界

目前以 [Mihomo 内核](/clients/mihomo/) 与 [sing-box 内核](/clients/sing-box/) 为代表的现代客户端，主流采用以下两种 DNS 增强模式来协同分流，它们各自的优缺点与冲突点差异极大：

| 对比维度 | `Fake-IP` 模式（虚构地址映射） | `Redir-Host` 模式（真实地址转发） |
| :--- | :--- | :--- |
| **返回给系统的 IP** | 立即下发 `198.18.0.0/16` 保留段内的虚构假 IP | 等待上游 DNS 查询结束后，返回真实的公网或内网 IP |
| **内存映射逻辑** | 在客户端内存维护一张「`198.18.x.x` ↔ 原始域名」映射表 | 不维护假 IP 表，客户端通过规则匹配与域名嗅探（Sniffer）二次识别 |
| **首包响应速度** | **极快**：省去本地等待真实 DNS 返回的时间，海外请求直接把域名打包交给远端节点解析 | **略慢半拍**：必须等待本地上游 DNS 至少返回一次真实结果后才能发起 TCP 建连 |
| **防污染与分流精度** | 极高：天然留存完整域名上下文，最契合 TUN 模式下的精准域名分流 | 依赖上游 DNS 分流准确度，若 `nameserver` 误配极易发生污染或泄露 |
| **典型冲突与坑点** | **强杀退出后缓存 `198.18.0.x` 断网**；部分内网软件、NAS、Docker、WSL2 及游戏反作弊不认假地址 | 内网与传统软件兼容性极佳，但若国内/国外上游配置混乱易导致国内 CDN 绕道 |

理解了这张表，就能看清为什么很多故障“换个模式就消失”：关于系统代理与 TUN 在这两种 DNS 模式下的底层交互差异，可进一步对照 [系统代理 vs TUN 与 DNS 深度解析](/guides/articles/tun-vs-system-proxy-dns/)。

## 二、关闭客户端后为何仍指向 `198.18.0.x` 打不开？缓存留存与无损清理

在日常求助中，最高频的一类 DNS 惊魂场景是：**明明刚才用着好好的，把代理软件一关（或者电脑强制重启、任务管理器强杀客户端后），浏览器打开常用网站突然彻底转圈失败，命令行执行 `nslookup` 竟然返回 `198.18.0.12` 这类诡异地址。**

### 1. 为什么客户端都关了，系统还在往 `198.18.0.x` 发包？

根本原因在于 **TTL 缓存与连接池的生命周期错位**：

1. **客户端退出钩子未能完整执行**：当你的客户端开启 `Fake-IP` 模式运行期间，Windows DNS Client 服务（`dnscache`）、macOS `mDNSResponder` 或 Linux 本地解析守护进程会忠实记住客户端下发的结果——比如把目标域名缓存为 `198.18.0.28`。正常在界面先关开关再点「退出」时，客户端会尝试撤销虚拟网卡与系统 DNS 接管；但如果你直接强杀进程、程序闪退或系统异常休眠，这套本地缓存依然原封不动留在内存里。
2. **浏览器内置 DNS 缓存与 HTTP/3 长连接保持**：现代 Chromium 内核浏览器（Chrome、Edge）及 Firefox 不仅依赖操作系统的 DNS 缓存，自己内部还维护了一套独立的 **HostResolverCache（浏览器内存 DNS 缓存）** 与 **QUIC / Socket 连接池**。即便你在命令行刷新了系统缓存，只要浏览器窗口没彻底关闭，标签页仍可能攥着旧的 `198.18.0.x` 地址反复尝试重连已经不存在的虚拟网卡，表现为“重启电脑前永远打不开”。
3. **网卡 DNS 被硬锁在回环地址**：在少数 TUN 模式异常崩溃或某些早年插件环境下，系统物理网卡（以太网或 WLAN）的 IPv4 首选 DNS 可能还停留在 `127.0.0.1`、`127.0.0.53` 或 `198.18.0.2`，代理进程退出后没有任何程序监听该端口，所有新解析请求全部石沉大海。

### 2. 四步无损诊断与缓存刷新实操

遇到关闭软件后疑似 `198.18.0.x` 留存断网，按以下四步只读观测加安全清理，一分钟内即可恢复，**绝对不需要重装系统或运行破坏性网卡重置脚本**：

**第一步：只读观测确认是否为 Fake-IP 残留**
在代理客户端已确认完全退出的状态下，打开终端执行只读域名查询（注意仅作观测，不改变任何配置）：

```powershell
# Windows PowerShell / CMD 只读观测
nslookup www.baidu.com
```

```bash
# macOS / Linux 终端只读观测
nslookup www.baidu.com
```

如果返回的 `Address` 显示 `198.18.x.x`（处于 `198.18.0.0/16` 保留网段内），或者提示 `127.0.0.1` / `198.18.0.2` 连接超时，即可 100% 确诊为 Fake-IP 缓存或网卡 DNS 指向残留。如果返回的是真实公网 IP 但浏览器依然报错「代理服务器没有响应」，则属于系统代理端口未清空问题，应转至 [TUN 与系统代理故障排查](/troubleshooting/tun-proxy/) 处理。

**第二步：刷新操作系统本地 DNS 缓存**
确认系统设置中的代理开关已关闭后，按系统平台执行标准缓存刷新指令：

```powershell
# Windows（无需破坏性重置网卡，仅刷新解析缓存）
ipconfig /flushdns
```

```bash
# macOS（根据系统版本刷新缓存守护进程）
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

```bash
# Linux（若使用 systemd-resolved）
sudo resolvectl flush-caches
```

**第三步：核查物理网卡 DNS 是否被异常锁定**
如果在执行 `ipconfig /flushdns` 后，`nslookup` 依然提示向 `127.0.0.1` 或 `198.18.0.2` 查询超时，请打开网络适配器图形面板检查（不要盲删网卡）：
- **Windows**：打开「控制面板」→「网络和共享中心」→「更改适配器设置」→ 右键当前物理网卡（WLAN 或以太网）→「属性」→ 双击「Internet 协议版本 4 (TCP/IPv4)」，确认是否被锁定了手动 DNS；若非公司静态办公网需求，将其切回**“自动获得 DNS 服务器地址”**并确定保存；同时顺手检查「Internet 协议版本 6 (TCP/IPv6)」DNS 设置。
- **macOS**：「系统设置」→「网络」→ 当前连接「详细信息」→「DNS」，查看列表里是否残存 `127.0.0.1` 或 `198.18.0.2`；若有且非用户自行填写，选中后点减号移除即可自动回退路由器 DHCP 下发的 DNS。

**第四步：彻底重启浏览器清除内存 Socket 池**
很多人做完前三步直接按 F5 刷新网页发现还是打不开，误以为没修好。实际上是因为浏览器后台进程还在驻留！必须**完全退出所有浏览器窗口与后台常驻托盘进程**（在 Chrome/Edge 右上角菜单点击「退出」，或在任务管理器确认浏览器进程已完全结束），也可以在浏览器地址栏打开内置网络状态页手动点击清除主机缓存与刷新 Socket 池后再重新访问。

### 3. 防复发规范：内网与系统服务纳入 `fake-ip-filter`

为了从源头减少 `198.18.0.x` 对本地系统和常用软件的干扰，在 Mihomo 生态（如 Clash Verge Rev 的 Merge 全局扩展配置）中，务必保留完善的 `fake-ip-filter` 排除名单，确保内网域名、时间同步和系统网络状态探测直接返回真实 IP：

```yaml
dns:
  enable: true
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  fake-ip-filter:
    - "*.lan"
    - "*.local"
    - "*.internal"
    - "localhost.ptlogin2.qq.com"
    - "+.msftconnecttest.com"
    - "+.msftncsi.com"
    - "time.*.com"
    - "time.*.gov"
    - "ntp.*.com"
    - "+.pool.ntp.org"
```

如果你发现即使加了过滤名单，公司 OA 客户端、特定网银安全控件或本地开发容器仍然和 `198.18.0.0/16` 水土不服，无需硬扛，直接在配置覆写中将 `enhanced-mode` 切换为 `redir-host`（并确保开启 `sniffer` 域名嗅探辅助规则匹配）即可一劳永逸消除假 IP 残留问题。

## 三、系统私有 DNS（DoT）与浏览器内置 DoH 为何会架空分流？

第二类极隐蔽的 DNS 故障通常发生在“网络看似没断，但分流规则完全不听使唤”的场景：例如明明写了把某个工作域名走直连或把 ChatGPT 走新加坡节点，客户端连接日志（`Connections`）里却看不到对应域名，只看到一串串纯 IP 连接，或者整个国外服务直接加载失败、海外平台判定所在地频频出错。

这类现象背后的元凶，十有八九是**操作系统级的加密 DNS（DoT）** 或 **浏览器内置的安全 DNS（DoH）** 与本地代理客户端产生了“双头抢权”。

### 1. Chrome / Edge 浏览器内置 DoH（安全 DNS）如何绕过客户端

Chrome、Microsoft Edge 与 Firefox 近年都在安全设置中默认或引导用户开启了**「使用安全 DNS（DNS-over-HTTPS / DoH）」**。开启后，浏览器不再把域名解析请求交给操作系统的系统 DNS 栈（即不再经过本地代理客户端在 53 端口或 TUN 网卡上设立的 DNS 拦截器），而是直接由浏览器内部通过 HTTPS 443 端口连向预设的公共 DoH 提供商。

这会引发三层连锁破坏：

1. **规则引擎变“瞎”**：由于解析请求根本没经过客户端内置 DNS 模块，在 `Fake-IP` 模式下客户端无法建立假 IP 映射，在 `Redir-Host` 模式下客户端也拦截不到解析记录。浏览器拿到的是一堆裸露的目标 IP；若未开启精准的 TLS SNI 嗅探，后续连接就只能落入纯 IP 规则或最后的 `MATCH` 兜底规则，大量本该按域名精准直连或指定国家节点的流量全部乱套。
2. **海外软件判定位址错位与风控触发**：如果浏览器安全 DNS 选的是**国内公共 DoH**，浏览器会把海外网站域名发往国内服务器解析（国内可能返回被污染的错误 IP，或者离国内最近的边缘节点）；而如果你在国外公共 DoH 列表里选了某家海外解析商，浏览器可能直接通过当前默认代理节点或直连发往该 DoH，返回的 CDN IP 归属国与你当前选中的代理落地节点归属国不一致。对地理位置与 CDN 拓扑极其敏感的 AI 平台和流媒体（如 Gemini、Netflix），极易因此触发地域风控或识别漂移。
3. **浏览器与系统其余软件结果打架**：浏览器自己走 DoH 拿到一组 IP，而电脑上其他软件走代理内核内置 DNS 拿到另一组 IP，导致同一账号在网页端和桌面端出现奇怪的连接中断。

**无损解决操作（桌面浏览器）**：
打开浏览器「设置」→「隐私和安全」→「安全」→ 找到**「使用安全 DNS」**，将其**关闭**（或者明确设为不使用自定义/自动加密提供商），把全部域名解析与加密传输统一交还给代理客户端内核内部的 DoH 模块处理。关于在客户端内如何配合代理转发规则，可继续对照 [连接不上排查树](/troubleshooting/cannot-connect/) 检查浏览器扩展是否也同步锁定了代理控制权。

### 2. Android「私人 DNS（DoT）」与 Windows 系统加密 DNS 冲突

除了浏览器，现代操作系统自身也引入了系统级加密 DNS，冲突表现同样明显：

- **Android 系统「私人 DNS（Private DNS / DoT）」**：Android 9 及以上系统在「网络和互联网 / 更多连接设置」中提供私人 DNS 选项，使用 853 端口的 DNS-over-TLS（DoT）。当你在手机上启用了 Clash Meta for Android、FlClash、Hiddify 或 v2rayNG（详情见 [安卓 VPN 与客户端安全选型](/vpn/android/)）时，Android 系统底层的网络框架会尝试把手动指定的私人 DNS 853 端口请求直接发往外网，甚至绕过 `VpnService` 的普通 DNS 捕获逻辑。
  - **典型故障表现**：如果手机里填了国内公共 DoT 地址，所有海外域名都被国内解析，代理软件丢失域名上下文甚至拿到被污染 IP；如果填了海外公共 DoT（如 Cloudflare 或 Google 的 DoT 主机名），在代理隧道尚未就绪或直连阻断环境下，手机直接提示**“无法连接到私人 DNS 服务器”**，整台手机无论国内国外全部断网！
  - **修复方法**：使用代理客户端期间，进入手机系统设置 → 网络与连接 → 私人 DNS，切换为**「关闭」**（部分手机“自动”模式下若当前 Wi-Fi 路由器下发了不可达 DoT 提示同样会触发断流，排障期一律先设为“关闭”）。
- **Windows 11 系统级网卡 DoH**：Windows 11 允许在「设置 → 网络和 Internet → WLAN/以太网 → DNS 服务器分配 → 编辑」中为指定 IPv4/IPv6 DNS 开启「DNS over HTTPS（自动模板或手动开启）」。如果在开启代理客户端的 TUN 模式或本地 DNS 接管时，系统网卡依然硬指定了带加密模板的公共 DNS，部分系统进程与 UWP 应用会直接走加密通道绕过客户端解析。**排障准则**：使用代理客户端时，保持 Windows 网卡 DNS 为「自动 (DHCP)」，加密 DNS 统一由客户端内核配置接管，不要在系统网卡和代理软件两处重复套娃开启加密 DNS。

## 四、国内外 DNS 分组配置失误：为何国内 CDN 绕道海外、国内站卡成幻灯片

排除了浏览器和系统私有 DNS 干扰之后，另一大高频痛点集中在**客户端自身的 DNS 配置文件写法有误**，最典型的体感是：“开启代理后，Google 和 YouTube 飞快，但打开淘宝、腾讯视频、阿里云盘或公司测试站却慢如蜗牛，甚至发现国内网站图片加载也要耗费好几秒。”

### 1. 国内 CDN 绕道海外的罪魁祸首

国内大型互联网服务全面使用多线智能 CDN（内容分发网络），其调度逻辑高度依赖**发起 DNS 查询的服务器所在地及客户端网段（EDNS Client Subnet）**：

- 当你用国内本地/国内加密 DNS 解析国内域名时，DNS 返回距离你所在省份、所属运营商（电信/联通/移动）最近的边缘机房 IP，下载和打开都是本地千兆满速。
- 一旦你的代理配置里**错误地把海外 DNS（例如 `8.8.8.8`、`1.1.1.1` 或走代理节点的境外 DoH）放进了默认 `nameserver` 且没有做域名分流过滤**，国内域名就会跑到海外 DNS 服务器去解析！海外服务器以为访客在国外，于是给你的电脑返回一个位于香港、新加坡、美国西海岸甚至欧洲的 CDN 节点 IP。哪怕你的分流规则随后判定这个目标域名走 `DIRECT`（直连），你的电脑依然在用国内宽带去硬连海外机房 IP，延迟瞬间飙升十倍、丢包卡顿不可避免；更糟糕的是，有些模糊的 `GEOIP,CN` 规则因为拿到了海外 CDN IP，干脆把原本该直连的国内大流量也误送进了机场付费专线隧道，白白烧光宝贵的月度或一次性流量包！

### 2. 厘清 Mihomo DNS 四大核心字段的正确分工

在 `Mihomo`（原 Clash.Meta）配置文件中，避免“国内绕道”与“海外污染”需要精准理解 `default-nameserver`、`nameserver`、`fallback` 与 `nameserver-policy` 的协作关系：

| 配置字段 | 核心技术职责 | 常见误配踩坑点 | 正确安全配置原则 |
| :--- | :--- | :--- | :--- |
| `default-nameserver` | **引导解析器**：专门用来解析其他 DoH/DoT 上游服务器自身的域名（如把阿里 DoH 域名解析出 IP） | 填入本身还需要域名解析的 DoH URL，造成“鸡生蛋、蛋生鸡”死循环无法启动 | 必须只填写**纯 IP 地址**的可靠国内 DNS（如运营商网关或已知可靠的纯 IP DoH/UDP 服务器），严禁写域名 |
| `nameserver` | **默认基础解析池**（通常建议定位为国内直连域名的快速解析层） | 直接把 `8.8.8.8` 或境外 DoH 塞入 `nameserver` 且不加分流，导致国内域名全绕道海外 | 配合 `fallback` 使用时，仅放置国内低延迟加密 DNS（如国内正规 DoH），保证国内 CDN 就近精准调度 |
| `fallback` | **海外防污染后备解析池**（配合 `fallback-filter` 与 `respect-rules` 使用） | 未配置 `respect-rules: true`，导致向海外 DNS 发出的解析请求在本地直连发包，继续被拦截或超时 | 放置海外安全加密 DNS（如 Cloudflare/Google DoH），并通过节点代理走远端安全解析 |
| `nameserver-policy` | **按域名集精准指定解析上游**（高优先级直通调度，减少并发猜谜） | 规则过时或未引入 `geosite:cn` / `geosite:private`，导致新出现的国内服务仍触发双路竞速 | 直接把 `geosite:private` 与 `geosite:cn` 明确锁定到国内 DNS，海外规则集直接指向代理侧 DNS，效率最高 |

以下是一段结构清晰、兼顾国内极速 CDN 与海外防污染的 Mihomo DNS 配置逻辑参考（具体需结合你使用的桌面端覆写模块与规则集名称核对，修改前务必备份原配置）：

```yaml
dns:
  enable: true
  ipv6: false
  listen: 0.0.0.0:1053
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  respect-rules: true
  default-nameserver:
    - 223.5.5.5
    - 119.29.29.29
  nameserver:
    - https://dns.alidns.com/dns-query
    - https://doh.pub/dns-query
  proxy-server-nameserver:
    - https://dns.alidns.com/dns-query
    - https://doh.pub/dns-query
  nameserver-policy:
    "geosite:private":
      - system
    "geosite:cn":
      - https://dns.alidns.com/dns-query
      - https://doh.pub/dns-query
    "geosite:geolocation-!cn":
      - https://1.1.1.1/dns-query
      - https://dns.google/dns-query
```

**特别留意两个容易被新手忽略的关键细节**：
1. **`proxy-server-nameserver`（节点域名专用解析）**：当你的机场节点服务器本身是以域名形式下发时，客户端启动必须先解析机场中转入口服务器的域名，才能连上节点。如果不设 `proxy-server-nameserver` 且默认解析走错了代理策略，就会陷入“没连上节点所以解析不了节点域名、解析不了域名所以连不上节点”的死锁！将其明确指定为国内加密 DNS（如阿里/腾讯 DoH），可确保中转入口永远秒速解析连通。
2. **`respect-rules: true`（让海外 DNS 查询遵循分流规则走代理）**：当配置里向海外 DoH（如 `1.1.1.1` 或 `dns.google`）发起域名查询时，如果不启用 `respect-rules: true`（或在旧版逻辑中未正确配置 `fallback-filter`），客户端会试图**本地直连**访问海外 DoH，结果请求在半路直接被超时丢包或引发 DNS 泄露；启用后，发往海外 DoH 的解析请求本身就会严格经过代理节点隧道送往远端安全执行。

### 3. IPv6 DNS 泄露导致绕道或双栈延迟飙升

国内越来越多家庭宽带（尤其是光猫默认开启 IPv6 后）与移动 4G/5G 网络会自动给设备分配公网 IPv6 地址和运营商 IPv6 DNS。很多机场品牌（例如站内档案收录的部分老旧专线或特定节点池）**仅完善转发 IPv4 流量，或客户端本地配置未正确接管 IPv6 DNS**。

当电脑同时拥有 IPv4 与 IPv6 双栈且代理端仅拦住了 IPv4 DNS 时，操作系统可能会优先通过未受控的本地 IPv6 网卡向运营商 IPv6 DNS 发出 `AAAA` 记录查询。轻则造成 DNS 泄露、网页卡在半加载等几十秒才回退 IPv4，重则直接导致海外站点返回不可达状态。在无明确纯 IPv6 机场节点支持的前提下，排障时在客户端 DNS 配置中保持 `ipv6: false`（不返回或屏蔽无用的境外 `AAAA` 解析），并在需要时核查本地网卡 IPv6 DNS 干扰，往往能立竿见影消除大量莫名其妙的卡顿。

## 五、面向 AI 工具（ChatGPT / Claude / Gemini）的防 DNS 泄露检查步骤

对于深度依赖 ChatGPT、Claude、Gemini 等生产力平台的用户来说，DNS 泄露带来的不只是“慢一点”，而是**真实地理位置暴露与出口不一致引发的风控拦截**。

结合站内过往实测档案的客观规律（详细分流策略可参阅 [AI 与流媒体 GeoIP 分流实战](/guides/articles/ai-streaming-geoip-routing/)）：在 [光速云](/brands/guangsuyun/) 2026-08-19 实测快照中，香港节点在 OpenAI 上几乎全数显示“仅 APP(HK)”而网页端受限，Gemini 在香港、日本、美国与台湾节点当时均有大面积失败记录（仅新加坡等特定区可用）；而在 [灵动云](/brands/lingdongyun/) 2026-07 实测中亦观测到部分新加坡与台湾广播节点出现 YouTube 送中（CN）。这意味着，当你已经费尽心思通过策略组把 AI 域名固定到了新加坡或日本节点后，**如果 DNS 解析本身发生了泄露或走错了地方，依然可能前功尽弃**。

以下是一套面向 AI 工具与高敏账号的**五步防 DNS 泄露只读检查流程**：

### 第 1 步：核查浏览器与系统层是否关闭独立加密 DNS

确认 Chrome/Edge 的「使用安全 DNS（DoH）」处于**关闭**状态；确认 Windows 网卡 DNS 为自动获取、Android 手机「私人 DNS」为**关闭**状态，确保没有任何浏览器或系统组件在底层私自外发 DNS 查询。

### 第 2 步：在客户端 `Connections` 与 `Logs` 核对 AI 域名的实际解析与命中规则

打开 Clash Verge Rev 或 v2rayN 的日志（Logs）与连接（Connections）监控面板，无痕打开 `chatgpt.com`、`claude.ai` 或 `gemini.google.com`，随后在连接列表搜索对应域名并检查三项特征：

1. **目标地址列显示为域名而非裸 IP**：如果看到 `chatgpt.com:443` 或清晰的域名标识，说明客户端完整保留了域名上下文（无论是 Fake-IP 还是开启嗅探后的 Redir-Host），规则命中无误。如果只看到一串孤立 IP 且规则行显示 `MATCH` 或 `GEOIP`，则极可能是浏览器 DoH 未关或 DNS 接管失败。
2. **规则（Rule）与出站节点（Chain）完全一致**：确认 `openai.com`、`chatgpt.com`、`anthropic.com`、`claude.ai`、`gemini.google.com` 均准确命中了对应的非香港固定策略组（例如日本或新加坡单一节点），且没有开启短间隔自动测速 `url-test` 在多国之间来回跳变。
3. **无并发泄漏日志**：观察 `Logs` 中是否出现向本地运营商 DNS IP 或国内 DoH 发送 `chatgpt.com` / `claude.ai` 解析请求的记录。正常配置下，此类境外敏感域名绝不应出现在国内 DNS 的查询记录中。

### 第 3 步：排查 WebRTC 本地 IP 暴露与 DNS 出口归属

对于浏览器端登录的敏感平台，除 DNS 本身外，**浏览器 WebRTC（网页实时通信）** 有可能绕过系统代理暴露本地局域网 IP 甚至真实公网入口特征；此外可利用正规的在线 DNS 泄漏检测页面（在浏览器打开后观察页面报告的 DNS 解析器所在国家与 ASN 归属）。

**正确判读标准**：
- **Fake-IP 模式下开启代理访问海外测试页**：如果你为海外域名配置了通过代理远端解析，检测页面应当只显示**与你当前选中落地节点同一地区（或该机房上游正规配置的境外解析商）的 DNS 服务器**；绝对不能出现中国大陆三大运营商（电信、联通、移动）或阿里/腾讯国内 DNS 的节点条目。
- **Redir-Host 模式下**：若检测结果出现了国内运营商或国内公共 DNS，说明 `fallback` 或 `nameserver-policy` 未能把海外域名隔离到代理侧解析，必须按前文第四节调整 `respect-rules: true` 与 `nameserver-policy`，切忌在存在明显 DNS 泄露的状态下反复登录主力付费 AI 账号。

### 第 4 步：核验节点自身是否已“送中”或地理定位异常

有时并非你本地配置了 DNS 泄露，而是你选用的那个机场节点本身在服务商侧遭遇了上游广播 IP 漂移（即站内 [YouTube 送中排查](/ai-media/youtube/) 与 [Gemini 解锁专题](/ai-media/gemini/) 反复提及的 `送中(CN)` 现象）。如果多方核对本地 DNS 均已严密隔离、浏览器 DoH 也已关闭，但访问 Gemini 依然报所在国家不支持或 Google 首页显示异常地区，请直接切换同区其他编号节点或跨国切换至实测验证可用的新加坡/日本/美国节点复测。

### 第 5 步：隔离本地局域网与终端工具链

如果你同时在电脑端运行 Cursor、Claude CLI 或终端脚本调用 AI API，请注意纯「系统代理」有时无法接管部分 CLI 进程的 DNS 或 UDP/HTTP 请求，可参考 [TUN 与系统代理故障指南](/troubleshooting/tun-proxy/) 与 [Windows 客户端选型矩阵](/guides/articles/windows-clients-guide/) 核对环境变量或按需切换单一的 TUN 模式，避免网页端不泄露、终端却在暗地里直连超时或泄露请求。

## 六、常见 DNS 故障症状与快速定位对照表

当你下次再遇到域名打不开、解析异常或卡顿时，直接对照下表锁定根因并执行对应可逆操作，无需盲目删库重装：

| 异常现象描述 | 高概率根本原因 | 优先只读观测方法 | 标准无损处理方案 |
| :--- | :--- | :--- | :--- |
| 退出代理软件后全网或部分站打不开 | `Fake-IP` `198.18.0.x` 缓存未刷或浏览器缓存未清 | 退出后终端跑 `nslookup`，看是否返回 `198.18.x.x` | 确认系统代理已关 → `ipconfig /flushdns`（或 macOS 刷缓存）→ 彻底重启浏览器 |
| 开启代理后打不开路由器、NAS、公司 OA | 内网域名未加入 `fake-ip-filter` 且未置顶 `DIRECT` | 看客户端 `Connections` 是否给内网域名分配了假 IP 并送往节点 | 把 `*.lan`、`*.local`、内网后缀加进 `fake-ip-filter` 并在顶部设为 `DIRECT`；或切回 `redir-host` |
| 客户端日志里目标变成纯 IP，规则失效 | Chrome/Edge 开启了安全 DNS（DoH）或安卓开了私人 DNS | 检查浏览器安全设置与手机私人 DNS 状态；查客户端是否启用 `sniffer` | 关闭浏览器 DoH，Android 私人 DNS 设为「关闭」，保留客户端核心 `sniffer` 嗅探 |
| 开了代理国内视频、网购、网盘加载极慢 | `nameserver` 误填入海外公共 DNS，国内 CDN 绕道国外 | 观测国内域名解析返回的 IP 归属地是否为境外机房 | 将 `nameserver` 设为国内加密 DNS，配合 `nameserver-policy` 按 `geosite:cn` 精确分流 |
| 节点明明已连上，全部海外网页打不开 | `proxy-server-nameserver` 缺失导致机场入口域名解析死锁，或本地 IPv6 DNS 失控 | 查看内核启动日志是否报解析机场节点域名超时，检查 `ipv6` 开关 | 补充纯 IP `default-nameserver` 与国内 `proxy-server-nameserver`，排障期将客户端 `ipv6` 设为 `false` |
| 挂着非香港节点，ChatGPT/Gemini 仍报地区风控 | 存在 DNS 泄漏、浏览器 WebRTC 暴露，或选用了广播定位飘移/送中节点 | 开日志查海外域名是否被国内 DNS 解析；用无痕窗测单节点与更换地区 | 补齐 `respect-rules: true` 与海外 `fallback`，剔除香港或送中编号节点，固定美/日/新纯净节点 |

遵循「先观测 `nslookup` 与日志、先清本地 DoH/DoT 干扰、再按国内外隔离修配置」的排障顺序，几乎所有 proxy 场景下的 DNS 疑难杂症都能在不破坏系统底层网络环境的前提下精准定位并解决。如果修完 DNS 依然遇到连接失败、客户端无法启动或 TUN 与开发容器冲突，请顺着站内排障分支继续查阅 [客户端无法启动排查](/troubleshooting/app-startup/) 与 [TUN 与系统代理混合故障](/troubleshooting/tun-proxy/)。
