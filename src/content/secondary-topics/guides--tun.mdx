几乎所有刚开始在电脑上配置代理工具的用户，都遇到过一个令人困惑的场景：桌面客户端里节点延迟显示只有三十多毫秒，Chrome 浏览器打开海外网页也流畅自如，可一旦切回终端运行 `git clone`、`curl` 或者启动 `claude code`、`npm install`，屏幕就卡在连接超时；又或者打开了 Microsoft Store 下载应用、启动某款需要联机的桌面游戏，流量却依然固执地走本地宽带直连，仿佛代理客户端根本不存在。

造成这种割裂体验的根本原因，并不在机场节点本身，而在于**系统代理（System Proxy）与 TUN 虚拟网卡模式所处的操作系统网络层级完全不同**。要真正用好桌面与命令行代理工具，必须先分清 L4/L7 应用配合与 L3 网络层接管的技术边界，再合理选定 `system`、`gvisor` 或 `mixed` 协议栈，并避开权限不足、双开环路以及 Docker 与局域网网段屏蔽等经典陷阱。

## 一、工作原理深度拆解：系统代理（L4/L7）vs TUN 虚拟网卡（L3）

理解网络数据包离开电脑之前的流转顺序，是判断自己该开系统代理还是开启 TUN 模式的唯一准绳。你可以把系统代理看作「礼貌的通知公告栏」，而把 TUN 模式看作「在小区大门口新修的强制安检闸机」。

### 1. 系统代理（HTTP / SOCKS5）：L4/L7 应用主动配合机制

当你在客户端（例如 [Clash Verge Rev](/clients/clash-verge-rev/) 或 [v2rayN](/clients/v2rayn/)）中打开「系统代理」开关时，软件并没有修改操作系统的网卡驱动，也没有拦截底层 IP 数据包。它实际上只做了两件非常轻量的事：第一，在本地环回地址 `127.0.0.1` 上开启一个混合监听端口（例如 `7897` 或 `10808`），准备接收 HTTP（L7 应用层）与 SOCKS5（L4/L5 会话传输层）格式的转发请求；第二，调用操作系统接口，在 Windows 注册表或 macOS 网络偏好设置中写入「当前系统的代理服务器地址为 `127.0.0.1:7897`」。

接下来的事情完全取决于**单个应用程序是否愿意遵守这个通知**。主流浏览器（Chrome、Edge、Safari、Firefox）以及基于 Electron 或系统网络库开发的常规桌面软件，在发起网页请求前会主动查询操作系统的代理设置，看到 `127.0.0.1:7897` 后便乖乖把请求打包发往客户端端口，再由 Mihomo 或 sing-box 核心根据分流规则决定直连还是送进机场节点。

但操作系统里存在大量**根本不理会系统代理通知**的程序。终端命令行工具通常直接调用底层系统套接字建连；部分独立桌面客户端为了控制网络行为而硬编码了直连逻辑；Windows 的部分 UWP 商店应用由于安全沙盒的回环隔离限制，甚至被系统禁止访问本地 `127.0.0.1` 端口；至于绝大多数使用 UDP 协议的游戏客户端、语音工具或基于 QUIC 传输的服务，标准 HTTP 代理更是天然无法承载其数据报文。

### 2. TUN 模式（虚拟网卡）：L3 网络层全局接管机制

**TUN（Network TUNnel）** 是操作系统内核原生支持的三层虚拟网络设备。与在应用层等待软件主动配合不同，开启 TUN 模式后，代理核心会向操作系统注册一张名为 `Meta`、`utun` 或 `tun0` 的虚拟网络适配器，同时修改操作系统的路由表，将默认网关指向这张虚拟网卡（或注入更细粒度的掩码路由规则）。

一旦路由接管生效，电脑上**几乎所有应用程序**发出的 TCP 与 UDP 原始 IP 数据包，无论该软件本身是否支持代理、是否读取环境变量、是否使用底层原始套接字，都会按照操作系统内核的路由决策，统一被送入虚拟网卡的队列中。代理核心（如 Mihomo 或 sing-box）从虚拟网卡读取这些三层 IP 数据包，重组出传输层会话并结合域名信息进行分流，最后再通过物理网卡（真实 Wi-Fi 或网线）把封装好的加密流量发送到远端机场服务器。

| 对比维度 | 系统代理（System Proxy） | TUN 虚拟网卡模式（TUN Mode） |
| :--- | :--- | :--- |
| **网络工作层级** | L4 / L7 应用与会话层（HTTP / SOCKS5） | L3 网络层（IP 数据包虚拟适配器接管） |
| **接管覆盖范围** | 仅限遵守系统代理的浏览器与部分 GUI 应用 | 几乎全系统进程（含终端 CLI、游戏、UWP、桌面工具） |
| **UDP 与 QUIC 支持** | HTTP 代理完全不支持 UDP；SOCKS5 需应用主动适配 | 原生捕获 TCP、UDP 与 ICMP 流量，适用游戏与语音 |
| **系统权限门槛** | 极低，普通桌面用户权限即可随时开关 | 较高，Windows 需 Service Mode 或管理员；Mac/Linux 需提权 |
| **对本地网络干扰** | 极小，极少影响局域网访问与虚拟网桥 | 较强，易与企业 VPN、Docker 网桥、WSL2 及反作弊冲突 |
| **异常退出后遗症** | 浏览器可能残留代理地址提示代理无响应 | 路由表或 Fake-IP 缓存未清理可能导致整机短时断网 |
| **日常推荐定位** | **日常网页浏览与轻度办公首选** | **命令行开发、商店下载、游戏与全托管按需开启** |

### 3. 决策实操：什么时候必须开 TUN？什么时候保留系统代理更稳？

在实际使用中，并不是把 TUN 模式设为永久常驻就一定更高级。遵循「够用即止、最小侵入」原则，可以按下面两份清单直接做选择：

**必须开启 TUN 模式的五类典型场景：**

1. **终端与编程辅助工具高频工作流**：你在终端频繁执行 `git push`、`curl`、`wget`、`pip`、`go get`、`cargo`，或运行 `claude code`、各类 AI CLI 工具且不想在每一个 Shell 会话和工具配置文件里反复手写 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量时，TUN 能一次性实现全局接管。
2. **Windows WSL2 与虚拟机联动场景**：当需要让子系统内部工具自然跟随宿主机分流规则，且你的 Windows 11 环境已按 [TUN 与系统代理及 DNS 深度对比](/guides/articles/tun-vs-system-proxy-dns/) 开启了镜像网络（`mirrored`）模式时，TUN 配合规则过滤能提供最接近原生 Linux 的无缝体验。
3. **系统商店与沙盒封装应用**：包括 Windows Microsoft Store 下载更新、部分依赖系统后台服务拉取资源的跨平台框架工具、以及默认忽略系统代理设置的独立桌面应用。
4. **海外游戏启动器与联机 UDP 流量**：诸如 Steam 商店社区之外的游戏客户端登录器、主机平台桌面联机辅助以及需要 UDP FullCone 转发的语音或游戏包，必须依赖三层网卡接管（同时注意竞技类强反作弊游戏的驱动兼容性）。
5. **需要严防应用绕过代理的隔离测试**：当测试某个海外桌面客户端是否存在直连探测或后台泄露时，只有 TUN 能确保其所有标准出站请求都经过代理规则引擎审计。

**保留系统代理更稳、不建议盲目开 TUN 的五类场景：**

1. **纯浏览器查资料与网页版 AI 办公**：如果你每天 90% 的时间只打开 Chrome、Edge 或 Safari 看文档、刷 YouTube 或使用网页版 ChatGPT、Claude 与 Gemini，系统代理没有任何虚拟网卡封装开销，CPU 占用极低且响应极其干脆。
2. **必须同时挂载公司企业 VPN 或零信任客户端**：诸如公司内网的 WireGuard、Cisco、Pulse 或各类政务办公 VPN 本身也会创建虚拟网卡并修改路由表，此时再开本地机场的 TUN 模式，两张虚拟网卡极易抢夺默认路由导致内网断连；保留系统代理（或在浏览器用插件隔离）反而能够和平共处。
3. **本地运行复杂 Docker 多网桥或生产容器环境**：如果宿主机正在跑多个自定义容器网段、数据库映射或 Kubernetes 本地集群，开启全局 TUN 很容易误把容器互访流量吸进代理或造成端口映射回环；开发中仅需要拉取少数海外依赖时，系统代理配合精准的终端代理环境变量更安全。
4. **非管理员权限的公司或学校受限电脑**：没有管理员权限安装服务模式时，强行折腾提权既可能触发企业安全审计，又容易因核心启动失败引发断网。
5. **同时使用多款代理工具或游戏加速器交替测试**：当你在 Clash Verge Rev、v2rayN 与商业游戏加速器之间频繁切换时，仅开系统代理的撤回与切换成本远低于反复安装和卸载虚拟网卡驱动。

## 二、核心参数实战：`system`、`gvisor`、`mixed` 协议栈与路由开关

当确认需要启用 TUN 模式后，无论是使用 Mihomo 内核的 [Clash Verge Rev](/clients/clash-verge-rev/)，还是使用 [sing-box](/clients/sing-box/) 与 [v2rayN](/clients/v2rayn/)，你都会在配置界面或 YAML/JSON 配置文件里遇到几个决定成败的关键参数：`stack`（协议栈类型）、`auto-route`、`auto-detect-interface` 与 `strict-route`。很多“开了 TUN 却巨卡、内存飙升或者局域网全断”的故障，根源全在这四个选项的误配。

### 1. 三种 TUN 协议栈深度对比：`system` vs `gvisor` vs `mixed`

代理核心从虚拟网卡接口拿到的，是一个个原始的三层 IP 数据包（只有源/目的 IP 和载荷字节），但上层的代理节点（VLESS、Trojan、Shadowsocks、Hysteria 2 等）工作在传输层流（TCP Stream）或数据报（UDP Packet）之上。因此，代理核心内部必须运行一套 TCP/IP 协议栈，负责把三层 IP 包重新组装还原成上层连接。这就是 `stack` 参数存在的意义：

| 协议栈模式 | 技术实现原理 | 吞吐性能与内存开销 | 兼容性与典型适用场景 |
| :--- | :--- | :--- | :--- |
| **`system`** | 调用操作系统原生内核网络栈接管数据包重组 | 吞吐效率最高、延迟最低、内存开销极低 | 适合追求极速大带宽下载或 Linux 软路由网关；在部分 Windows 杀毒防火墙或复杂容器网桥下偶尔出现兼容阻断 |
| **`gvisor`** | 在代理进程内部（用户态）嵌入独立的 Go 语言网络协议栈处理全部包重组 | CPU 与内存占用相对较高，极限单线程吞吐略低于内核栈 | 不依赖宿主机复杂的内核转发规则，跨系统一致性与防火墙穿透兼容性极强；适合疑难环境兜底或容器隔离场景 |
| **`mixed`** | **混合分流策略**：TCP 流量交由高效的 `system` 栈处理，UDP 流量交由稳健的 `gvisor` 栈处理 | 兼顾接近原生内核的 TCP 高速下载与较低的总体负载 | **绝大多数 Windows 与 macOS 桌面用户的默认首选**，既避免了纯 `system` 栈下某些软件 UDP 异常，又保住了网页与下载吞吐 |

在实际排查中记住一条实用经验：**平时一律保持 `mixed`**。只有当你发现开启 `mixed` 后某些软件打开极慢、或者 WSL2/虚拟机无论怎么调都连不上网络时，先尝试把协议栈临时切换为纯 `gvisor` 测试；反之，如果你在物理性能充沛的 Linux 主机上跑千兆大流量测试且确定防火墙规则干净，再切换为纯 `system` 压榨性能。

### 2. `auto-route`、`auto-detect-interface` 与 `strict-route` 开关逻辑

除了协议栈，控制虚拟网卡如何改写系统路由表的三个核心开关同样不能含糊：

- **`auto-route`（自动设置全局路由）**：在桌面端使用 TUN 模式时，这个开关**几乎必须开启**。打开后，Mihomo 或 sing-box 会在启动虚拟网卡时自动向操作系统写入覆盖默认流量的路由规则，让系统把出站包交到虚拟网卡；关闭软件时自动撤销这些路由。如果你手动关闭了 `auto-route`，那么虚拟网卡虽然创建出来了，但系统根本不知道要把流量发给它，结果就是“TUN 开关显示已打开，但终端依然走直连”。只有极少数在路由器上手动编写策略路由表的进阶玩家才会关闭 `auto-route`。
- **`auto-detect-interface`（自动识别物理出站网卡，Mihomo 关键防环路参数）**：试想一个死循环问题——当代理核心把默认路由全部指向了虚拟网卡后，代理核心自己想把加密后的数据包发往机场服务器时，操作系统一看路由表，又把这包发回了虚拟网卡，自己接管自己，瞬间陷入无限死循环。开启 `auto-detect-interface: true` 后，内核会自动探测当前电脑真正连接互联网的物理网卡名称（如 `WLAN` 或 `en0`），并强制将代理核心自身的出站请求直接绑定到那张物理网卡上，彻底切断环路。**桌面端务必保持此项开启**。
- **`strict-route`（严格路由模式）**：这个开关的作用是收紧系统路由策略，防止某些系统服务或 IPv6 流量在多网卡环境下绕过 TUN 泄漏到物理直连网关。听起来很安全，但它的副作用非常明显：在部分 Windows 宿主机或虚拟化环境中，开启 `strict-route` 后会导致同一局域网内的其他设备（如 NAS 共享文件夹、局域网打印机）、WSL2 网桥甚至部分本地服务无法正常握手。因此，**普通桌面用户默认建议保持关闭（`false`）**；只有在确有严格的防路由泄漏测试需求，且已经把全部私有局域网段配置进排除列表时，才考虑按需启用。

### 3. 为什么 TUN 模式必须协同 DNS 接管？

很多用户只打开了 TUN 开关，却把配置文件里的 `dns` 模块删掉或禁用，结果发现原本好好的规则分流（Rule 模式）突然失灵，或者所有网站都打不开。原因很简单：浏览器走系统代理时，是直接把完整域名（如 `claude.ai`）发给代理端口的；而进入 TUN 虚拟网卡的数据包在三层网络中只有目标 IP 地址，没有明文域名。

因此，TUN 模式必须配合客户端接管 DNS 解析：

- 在 **Fake-IP** 模式下，客户端提前给域名分配一个 `198.18.0.0/16` 保留网段的虚拟地址，应用程序连接该假 IP 时，内核直接在内存映射表里查回原始域名并精准执行规则分流；
- 在 **Redir-Host** 模式下，客户端拿到真实解析结果的同时，依赖 `sniffer`（域名嗅探，读取 TLS 握手 SNI 或 HTTP Host）反推域名来匹配规则。

关于 Fake-IP 与 Redir-Host 的详细取舍、以及如何配置 `fake-ip-filter` 避免 Windows 误报无网络或微信扫码卡顿，可以前往 [系统代理 vs TUN 与 DNS 机制深度文章](/guides/articles/tun-vs-system-proxy-dns/) 查看完整对照表；若遇到假 IP 残留导致的断网，则可联动 [DNS 错误排查专题](/troubleshooting/dns/) 处理。

### 4. 标准桌面端 TUN 配置片段参考

为了方便核对你的机场订阅或覆写配置是否合理，下面给出一段面向桌面端 Mihomo（Clash Verge Rev）的常规稳健 TUN 配置模板结构：

```yaml
tun:
  enable: true
  stack: mixed
  auto-route: true
  auto-detect-interface: true
  strict-route: false
  dns-hijack:
    - "any:53"
    - "tcp://any:53"
  route-exclude-address:
    - "192.168.0.0/16"
    - "172.16.0.0/12"
    - "10.0.0.0/8"
```

如果你使用的是原生 **sing-box** 生态（例如在官方 SFM 或通过自定义 JSON 配置），对应的入站管线也遵循同样的三要素思路：`stack` 设为 `mixed`、`auto_route` 设为 `true`、`strict_route` 默认保持 `false`，并通过 `route_exclude_address` 保护内网与容器段不受接管。

## 三、分平台权限配置实操：Windows Service Mode、macOS 与 Linux `tun0`

在现代操作系统中，普通应用程序无权随意创建网络适配器并篡改系统路由表。不同平台为解决这个最小权限边界，各自设计了不同的提权路径。这也是为什么很多新手点了 TUN 开关却毫无反应的最大拦路虎。

### 1. Windows：Clash Verge Rev Service Mode 与 v2rayN 管理员提权

Windows 环境下存在两种主流提权架构：

**路线 A：安装系统服务模式（以 Clash Verge Rev 为代表）**
如果你平时以标准普通用户权限打开桌面软件，推荐优先采用安装服务模式（Service Mode），而不必每次都把整个图形界面跑在管理员权限下（后者容易导致拖拽导入本地配置文件受阻或触发高权限安全风险）。实操步骤如下：

1. 先暂时关闭客户端界面上的「系统代理」开关。
2. 进入左侧或设置栏中的 **Service Mode（服务模式）** 选项，点击「安装（Install）」。
3. Windows 会弹出用户账户控制（UAC）提权确认框，点击「是」授权后台服务注册到系统服务管理器。
4. 观察界面指示状态，确认服务已变为 **运行中（Active / Installed）**。若杀毒软件拦截了 `verge-mihomo-service` 相关组件，需在确认安装包来自官方渠道且校验过哈希后谨慎排查安全软件拦截记录。
5. 服务就绪后，再回到主页打开 **TUN 模式** 开关，此时托盘与网络适配器列表里即可看到新建的虚拟网卡。

**路线 B：以管理员身份启动调度核心（以 v2rayN 为代表）**
根据 [v2rayN 全能配置指南](/clients/v2rayn/) 的核心架构，v2rayN 的 Tun 模式依赖底层调度的 `sing-box` 核心去申请 Windows 虚拟网卡驱动（Wintun）。如果你直接双击桌面普通图标启动 v2rayN，在界面底部开启 `Tun 模式` 时通常会弹出权限不足提示或静默失效。正确做法是：先关闭主界面上的自动系统代理，完全退出软件；随后右键点击 `v2rayN.exe` 选择「以管理员身份运行」（或在属性兼容性中勾选管理员运行，也可在软件内部设置开启以管理员模式启动相关的 Tun 参数），启动后再打开 Tun 开关即可成功接管全系统流量。

### 2. macOS：系统密码授权与 `utun` 虚拟接口机制

在 macOS 上（涵盖 Apple Silicon M 系列与 Intel 机型），内核通过系统原生的 `utun`（用户态隧道）接口实现三层接管。相比 Windows，macOS 不需要额外下载第三方虚拟网卡驱动文件，但同样需要明确的管理员授权：

1. 在 Clash Verge Rev、FlClash 或官方 SFM 等桌面端中开启 TUN 前，先确认「系统代理」已关闭。
2. 首次点击启用 TUN 时，客户端通常会调用 macOS 提权接口，弹出系统级授权窗口要求输入开机密码或触控 ID，用于为内核核心赋予绑定 `utun` 接口与修改路由表的权限（部分客户端在设置里也提供安装核心提权辅助工具的按钮）。
3. 如果你安装的是未经苹果公证或处于沙盒模式的应用（例如来自 App Store 的部分轻量化客户端，如 Clash Mi、Karing 等），它们走的是苹果标准的 `NetworkExtension`（VPN 扩展）系统机制，首次打开会跳转到「系统设置 — 隐私与安全性」或弹出「是否允许添加 VPN 配置」的确认提示，点击允许并输入开机密码即可自动分配一个类似 `utun4` 或 `utun5` 的虚拟接口。
4. 想确认 macOS 下 TUN 是否真的接管成功，可以在终端运行 `ifconfig` 查找带有 `198.18.0.1` 或对应 TUN 网段地址的 `utun` 设备，或者直接运行一次 `curl` 测试境外可达性。

### 3. Linux 桌面与无桌面端：`tun0` 网卡与 `CAP_NET_ADMIN` 免 root 授权

在 Linux（Ubuntu、Debian、Fedora、Arch 等）下创建 `tun0` 或 `Meta` 虚拟接口，传统做法是用 `sudo` 以 root 权限启动整套程序，但这在桌面环境中既不安全，又会导致图形界面环境变量、桌面托盘图标与配置文件归属权混乱。更规范的 Linux 工程做法是使用内核的细粒度权能机制 **`CAP_NET_ADMIN`**。

当你通过 `.deb` 或 `.rpm` 安装 Clash Verge Rev 等规范打包的桌面客户端时，安装脚本往往已经帮你配置好了后台服务权限或提权策略；而如果你使用的是 `.AppImage` 便携包、单独运行 `mihomo` / `sing-box` 二进制核心，或者在无桌面服务器中使用 [v2rayA](/guides/articles/linux-openwrt-clients-guide/)，可以单独赋予核心二进制文件网络管理权能，而不需要把整个 GUI 进程暴露在 root 权限下：

```bash
# 仅赋予核心二进制文件创建虚拟网卡与操作路由表所需的最小网络权能
sudo setcap cap_net_admin,cap_net_bind_service=+ep /usr/local/bin/mihomo

# 核对内核是否已存在 /dev/net/tun 字符设备
ls -l /dev/net/tun
```

授权完成后，用普通用户身份启动客户端并开启 TUN，`ip addr` 命令输出中即可看到活跃的 `Meta` 或 `tun0` 接口，且路由表已自动指向该设备。

## 四、高频故障排障：双开环路、Docker/WSL2 断网与局域网屏蔽恢复

开启 TUN 模式后，90% 的疑难杂症都集中在「模式冲突」与「路由误吞」两个方面。掌握下面三类故障的精准定位手法，可以在不重装系统、不运行破坏性网络重置脚本的前提下，一分钟内安全恢复网络秩序。

### 1. 严禁同时双开「系统代理 + TUN」：环路与假卡顿特征

许多新手认为「把系统代理和 TUN 模式同时打开等于双倍保险」，实际上这恰恰是桌面端最常见的自伤操作。当你同时激活这两个开关时，系统内会发生以下混乱：

1. **流量路径分裂**：浏览器读取 `127.0.0.1:7897` 走应用层代理端口，而后台进程、终端和浏览器内部的某些 QUIC 连接却直接掉进了虚拟网卡，两路流量对同一目标站点建立并发会话。
2. **DNS 缓存与日志错乱**：如果浏览器插件或代理软件的端口与虚拟网卡路由没有做到完美隔离，或者开启了系统代理保护的同时又安装了其他调试抓包工具，请求包可能在本地环回口与虚拟网卡之间反复横跳，客户端连接日志里会瞬间刷出成百上千条相同目标的递归连接记录（即**本地路由环路**），导致 CPU 飙升、风扇狂转且网页彻底卡死。
3. **关闭不彻底引发后遗症**：你以为关掉了 TUN 就恢复了直连，结果忘记系统代理开关还挂在 `127.0.0.1`，导致退出软件后全部网页打不开。

记住铁律：**同一台设备上，同一时刻只开一种模式**。日常用系统代理，就把 TUN 关掉；需要接管终端或游戏打开 TUN 时，务必把系统代理开关拨回关闭状态。如果已经出现残留，请立即参照 [TUN 与系统代理故障汇总](/troubleshooting/tun-proxy/) 执行无损清理检查。

### 2. Docker、WSL2 与局域网 NAS/打印机被屏蔽排障

在 Windows 与 Linux 上启用 TUN 后，开发者最常碰到两类本地通信失联：一类是打不开局域网路由器后台（如 `192.168.1.1`）或挂载不了群晖 NAS、网络打印机；另一类是 Docker Desktop 容器无法联网、或者 WSL2 Ubuntu 子系统 `apt update` 一直卡在解析阶段。

**为什么局域网与 Docker 会断联？**
一方面，如果配置中误开启了 `strict-route`，或者订阅下发的规则把原本该直连的内网地址送进了 Fake-IP 与代理队列，局域网设备就会失联；另一方面，WSL2 默认处于独立虚拟网桥（NAT 模式）下，Docker 容器默认使用 `172.17.0.0/16` 等私有网桥段，它们发出的请求穿过网桥来到宿主机时，往往被宿主机防火墙视为外部入站连接而被拦截，或者拿到了宿主机 Fake-IP 返回的 `198.18.x.x` 假地址却在子系统里找不到回程路由。

**分层排查与安全修复步骤：**

1. **排除私有与容器网段**：确保配置文件中的 `route-exclude-address` 明确包含 `192.168.0.0/16`、`172.16.0.0/12`、`10.0.0.0/8` 以及局部链路网段 `169.254.0.0/16`，并且不要开启 `strict-route`。
2. **加入 Fake-IP 过滤列表**：确保内网域名（如 `*.lan`、`*.local`、企业内部域后缀）已经写入客户端的 `fake-ip-filter` 清单，防止内网域名被映射成假 IP。
3. **针对 Windows 11 + WSL2 开启镜像网络**：在 Windows 用户目录 `.wslconfig` 中配置 `networkingMode=mirrored` 与 `dnsTunneling=true` 并执行 `wsl --shutdown` 重启子系统，即可让 WSL2 与宿主机共享网卡视图，彻底消除 NAT 网桥隔离。
4. **开发容器极简稳妥方案（无冲突）**：如果你使用的是 Windows 10 或不便调整复杂网桥，最稳的做法其实是**暂时关闭 TUN 模式**，只保留客户端的「系统代理」并打开「允许局域网连接（Allow LAN）」，然后在 Docker Desktop 的代理设置页或 WSL2 的 Shell 中显式配置宿主机代理端口，开发完毕后再切回日常模式。

### 3. 企业 VPN 共存冲突与异常断网的无损回退步骤

当个人代理的 TUN 模式遇上公司办公必需的零信任 VPN、远程桌面拨号或硬件防火墙客户端时，两套三层隧道驱动必然争夺默认网关（`0.0.0.0/0`），往往表现为“一开公司 VPN 就上不了外网，一开机场 TUN 就掉出公司内网”。稳妥的共存办法是**关闭机场客户端的 TUN 模式**，仅用「系统代理」配合浏览器代理切换扩展（仅将需要走机场的境外域名指向本地端口，其余全部直连或交给企业 VPN 路由），或者在工作机和个人设备之间做好物理隔离。

如果不幸因为强制关机、软件崩溃或误杀进程，导致关闭软件后出现「所有网站均无法打开」「网卡 DNS 被锁死在本地地址」或「浏览器提示代理服务器没有响应」，**千万不要去下载来路不明的一键网络重置工具**，而是严格按照以下无损回退顺序恢复：

1. **重新正常打开并规范退出客户端**：很多时候重新打开一次客户端、手动依次关闭「TUN 模式」和「系统代理」、再从托盘正常点击「退出」，软件自带的清理钩子就会自动把虚拟网卡与路由表恢复原状。
2. **核查操作系统代理勾选框**：进入 Windows「设置 — 网络和 Internet — 代理」或 macOS「系统设置 — 网络 — 当前连接 — 代理」，手动确认 HTTP、HTTPS 与 SOCKS 代理开关全部处于关闭状态。
3. **清理残留的 Fake-IP DNS 缓存**：Windows 在终端执行 `ipconfig /flushdns`，macOS 执行刷新 mDNS 缓存命令，并彻底关闭重开一次浏览器，消除浏览器内存中残留的 `198.18.x.x` 假地址连接。
4. **检查物理网卡属性与适配器状态**：进入系统网络适配器列表，确认真实的 Wi-Fi 或以太网网卡 IPv4 设置依然为「自动获得 IP 地址」和「自动获得 DNS 服务器地址」；如果看到已经退出的代理软件还遗留了僵尸虚拟适配器，右键禁用或通过软件自身服务卸载功能移除即可恢复正常直连。
