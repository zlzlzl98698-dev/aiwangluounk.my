在开源代理工具的技术演进史上，如果说 [Mihomo（原 Clash.Meta）](/clients/mihomo/) 代表了对传统 Clash YAML 生态的延续与现代化升级，那么 **`sing-box`** 则代表了彻底推倒历史包袱、从零设计的「**新一代通用代理平台（Universal Proxy Platform）**」。

凭借更严谨统一的模块化架构、极低的内存与 CPU 资源占用、对现代传输协议（VLESS-Reality、Hysteria 2、TUIC、AnyTLS 等）的快速支持，以及二进制规则集（`SRS`）带来的性能飞跃，sing-box 已经迅速渗透进官方原生移动/桌面端（`SFI` / `SFA` / `SFM`）、经典多核工具 `v2rayN`、新手友好客户端 `Hiddify` 与 `Karing`，以及现代 OpenWrt 软路由插件 `HomeProxy` 和 `PassWall2`。然而，由于绝大多数国内机场依然默认下发 Clash YAML 订阅，许多新手在初次接触 sing-box 时往往被「YAML 与原生 JSON 的格式断层」和「NekoBox 仿冒风险」卡在门外。本专题将系统拆解 sing-box 生态全景、多平台客户端选型边界与订阅转换实操对策。

## 一、sing-box 内核技术特点：为什么被称为新一代通用代理平台？

早期的代理生态长期处于工具碎片化状态：想用某项新协议要装 Xray，想用复杂分流规则要装 Clash，想建 QUIC 加速要单独启动 Hysteria 客户端。sing-box 的设计初衷，就是用单一、标准化的 Go 语言核心引擎，统一接管所有主流入站、出站、路由与 DNS 管线。

### 1. 高度解耦的四大管线模块

不同于 Clash 配置文件里把策略组与简单规则列表直接平铺的模式，sing-box 的原生配置文件采用结构严谨的 **JSON** 格式，将网络处理过程拆分为四个彼此独立又精确衔接的管线：

- **`inbounds`（入站监听）**：定义流量如何进入 sing-box 核心，可以是本机混合代理端口（`mixed`）、透明代理转发口（`redirect` / `tproxy`），也可以是接管全系统三层流量的虚拟网卡（`tun`）。
- **`outbounds`（出站节点与策略组）**：不仅包含具体机场节点（VLESS、Trojan、Shadowsocks、Hysteria 2、AnyTLS 等），还将「直连（`direct`）」、「拦截（`block`）」、「DNS 处理（`dns`）」以及类似 Clash 的手动选择（`selector`）与自动测速（`urltest`）统统抽象为标准的出站节点。
- **`route`（统一路由管线）**：按顺序评估每一条入站连接的协议嗅探结果、目标域名、GeoIP、进程名称、端口或二进制规则集（`rule_set`），决定把它交给哪一个 `outbound` 处理；其中 `route.rules` 中支持动作（`action`）机制（在 1.11 及以上现代版本中进一步统一了嗅探 `sniff` 与解析 `resolve` 动作）。
- **`dns`（独立 DNS 路由与防污染引擎）**：在 sing-box 中，DNS 服务器列表与域名分流规则同样以独立的规则管线运行，支持 DoH、DoT、DoQ 加密解析以及 `fakeip` 虚拟地址分配，避免了传统核心里复杂的隐式回环。

### 2. 二进制规则集（`.srs`）与移动端极低功耗

早期代理核心加载完整地理数据库（`.dat` 或大型文本规则集）时，往往要消耗几十 MB 内存，极易触及 iOS `NetworkExtension` 约 50MB 的内存上限，或拖垮低配路由器。sing-box 原生主推预编译的 **SRS（sing-box rule-set）二进制规则集**，把海量域名后缀和 CIDR 网段压缩为紧凑的内存友好格式，加载速度极快且几乎不产生额外 GC（垃圾回收）波动，这使得手机端运行 sing-box 时的发热和后台掉电通常表现优异。

## 二、sing-box 全平台客户端矩阵与 `NekoBox` / `Nekoray` 风险提醒

与 Mihomo 一样，普通用户日常接触的是基于 sing-box 内核封装的各平台前端软件。结合站内 `PROXY_CLIENTS` 安全台账，sing-box 生态已经分化出「官方原生客户端」「多核心集成端」「跨端格式转换封装端」与「OpenWrt 软路由端」四大阵营：

| 客户端 / 插件名称 | 覆盖运行平台 | 底层核心模式 | 订阅格式友好度 | 站内台账定位与硬性安全 / 维护提示 |
| :--- | :--- | :--- | :--- | :--- |
| **sing-box 官方客户端 (SFI / SFA / SFM)** | iOS/iPadOS (`SFI`) / Android (`SFA`) / macOS (`SFM`) / Linux | sing-box 原生 | **不直接兼容 Clash YAML**；仅认原生 JSON | 性能与稳定性极佳的官方参考客户端；没有 sing-box 订阅的普通新手上手难度高 |
| **Hiddify** | Windows / Android / iOS/iPadOS / macOS / Linux | sing-box | **极高**（自动识别多格式订阅并转换） | 界面简洁，自动选点与跨五端一致，新手友好；注意核对官方开源端与商店版一致性 |
| **Karing** | Windows / Android / iOS/iPadOS / macOS / Linux | sing-box | **极高**（兼容多种常见订阅与规则管理） | 面向新手的跨平台配置工具，iOS 主走外区 App Store 分发，适合替代复杂手动转换 |
| **v2rayN** | Windows / macOS / Linux | Xray / sing-box 多核心 | **高**（支持通用节点链与多种核心调度） | 桌面经典主力，可在核心设置按需切至 sing-box；下载须区分是否包含核心依赖包 |
| **HomeProxy** | OpenWrt 软路由 | sing-box | 需配好机场转换或面板适配（界面直接建构规则） | 面向现代 OpenWrt `fw4`（`nftables`）环境的原生插件，安装前须确认软件源版本 |
| **PassWall2** | OpenWrt 软路由 | Xray / sing-box | **高**（支持通用订阅节点与双核心混合调度） | 节点分流清晰，兼容广泛；低闪存硬路由部署前务必检查 `/overlay` 空间与依赖完整性 |
| **NekoBox for Android** | Android | sing-box | 高（支持多格式导入） | **高危安全警告：项目维护资源有限，严禁下载 Google Play 上已被第三方控制的同名应用** |
| **Nekoray（历史桌面衍生端）** | Windows / Linux | 早期 sing-box / Xray | 中 | **维护提示**：存在核心分叉与长期维护节奏问题，不建议新用户优先部署，应选 `v2rayN` 或 `Hiddify` |

### 1. 官方原生端系列（SFI / SFA / SFM）：纯粹但高门槛

sing-box 官方团队亲自维护了全套苹果与安卓原生客户端，简称 **SFI**（for iOS/iPadOS）、**SFA**（for Android）和 **SFM**（for macOS，另支持 Apple TV）。它们最大的优点是**零多余界面冗余、原生紧跟最新内核特性、与苹果系统网络扩展契合极佳**；但最大的劝退点在于官方坚决保持「内核工具」定位，**没有在前端内置兼容 Clash YAML 订阅的解析转换器**。如果机场不提供 sing-box 专属订阅地址，普通用户面对空白的 JSON 配置导入框几乎寸步难行。

### 2. 新手友好封装端：`Hiddify` 与 `Karing`

为了解决官方客户端不懂机场通用格式的问题，社区诞生了 `Hiddify` 与 `Karing` 两款同样以 sing-box 为底座、但专门针对日常订阅优化的跨平台工具：

- **`Hiddify`**：全免费开源，界面极简，在 Windows、Android、iOS、macOS 与 Linux 上均保持一致的交互。你只需复制机场的通用订阅链接粘贴进去，它会自动探测是 Clash、V2Ray Base64 还是 sing-box 格式，并套用预置好的国内外分流规则。
- **`Karing`**：同样覆盖五大系统平台，特别在 iOS 端通过外区 App Store 分发，为暂未购买付费版 `Shadowrocket` 或 `Stash` 的用户提供了可靠的免费入门渠道。相比 Hiddify，Karing 对自定义规则集、多订阅合并与策略组微调的自由度通常更丰富一些。

### 3. 多核心桌面主力 `v2rayN` 与 OpenWrt 软路由端

- **桌面端 `v2rayN` 切换 sing-box 核心**：熟悉单节点管理的老用户无需抛弃 [v2rayN](/clients/v2rayn/)。现代版本 v2rayN 已全面支持 Windows、macOS（注意区分 Apple Silicon 与 Intel）及 Linux，并允许在「设置 — Core 类型设置」中把 `VLESS`、`Hysteria 2` 或全局流量指定给内置的 `sing-box` 内核执行。下载时切记检查发布包是否包含 core 运行文件。
- **OpenWrt 软路由：`HomeProxy` vs `PassWall2`**：如果你运行的是官方较新版 OpenWrt（基于 `fw4` / `nftables` 防火墙），希望路由器也用上轻量高效的原生 sing-box 引擎，`HomeProxy` 是架构最契合的现代界面；而如果你的软路由需要同时兼容老旧节点格式、或者需要部分协议走 Xray、部分协议走 sing-box，`PassWall2` 依然是稳妥之选。部署前请严格按照 [Linux 与 OpenWrt 软路由实战指南](/guides/articles/linux-openwrt-clients-guide/) 核实固件版本与 `/overlay` 闪存空间。

### 4. 重点安全警示：`NekoBox` Play 商店第三方控制风险与 `Nekoray` 隐患

在中文搜索引擎与过往几年的教程里，经常能看到推荐安卓端 `NekoBox` 与桌面端 `Nekoray`。针对这两款工具，站内台账必须给出最明确的安全划界：

1. **`NekoBox for Android` 的双重风险**：一方面，站内 `PROXY_CLIENTS` 明确记录该开源项目「维护资源有限」，新协议兼容性与问题修复难以保证长期及时；另一方面，**官方资料特别发出严厉警告：绝对不要下载 Google Play 商店上已被第三方控制的同名 `NekoBox` 应用！** 当一款安全敏感的网络工具在应用商店被第三方接管或上架同名包时，其代码与原本开源仓库之间的一致性已无法保障，存在被植入广告追踪甚至窃取订阅凭据的风险。安卓用户应遵循 [Android 客户端安全选型指南](/guides/articles/android-clients-guide/)，直接选用经官方仓库签名核验的 `v2rayNG`、`FlClash`、`Clash Meta for Android`、`Hiddify` 或 `Karing`。
2. **桌面端 `Nekoray` 维护滞后提醒**：早期的桌面软件 `Nekoray` 曾是不少人在 Windows/Linux 上体验 sing-box 核心的过渡工具，但随着原维护分支出现停滞与多方接手分叉，新版本 sing-box 内核的语法变更（尤其是 1.11+ 的配置字段演进）往往导致旧版壳程序频繁报错或无法匹配新机场协议。桌面端新用户已没有任何理由再折腾 `Nekoray`，直接选择持续活跃迭代的 `v2rayN`（可自由切 sing-box 内核）或 `Hiddify`、`Karing` 更为稳妥。

## 三、核心痛点深挖：Clash YAML 与 sing-box JSON 转换困局

在实际选型中，阻挡 80% 用户用上原生 sing-box（尤其是 `SFI`/`SFA`/`SFM` 与 `HomeProxy`）的最大障碍，既不是软件安装，也不是节点协议，而是**上下游订阅格式的结构性错位**。

### 1. 为什么国内机场多提供 Clash YAML 而非原生 sing-box JSON？

浏览站内 31 家机场品牌库（如开放通用订阅的 [光速云](/brands/guangsuyun/)、[一翻云](/brands/yifan/)、[极连云](/brands/jilian/)、[光年梯](/brands/guangnian/)、[梯子云](/brands/tiziyun/)、[可信云](/brands/kexin/)、[速界](/brands/sujie/) 等），面板后端最普及的通用下发标准依然是两类：面向 `Clash / Mihomo` 的 **YAML 订阅**，以及面向 `v2rayN / Shadowrocket` 的 **Base64 节点列表**。仅有少数服务商或集成新版后端面板的机场，会额外提供一个专门的 `sing-box` 订阅按钮。

之所以存在这种延迟，是因为从配置结构上讲，Clash YAML 与 sing-box JSON 完全属于两套语法体系：

| 核心差异维度 | Clash / Mihomo YAML 体系 | sing-box 原生 JSON 体系 | 转换时最容易断裂的痛点 |
| :--- | :--- | :--- | :--- |
| **文件语法与容错** | YAML 缩进敏感，支持注释与客户端本地 Merge 覆写 | 标准 JSON 严格禁止尾部逗号与注释（部分衍生支持 JSON5/扩展但官方推荐标准 JSON） | 手改配置多一个逗号或少一个括号即导致整个核心拒绝启动 |
| **策略组与节点定义** | `proxies` 存节点、`proxy-groups` 存选择组，互相分离 | 全部统一放入 `outbounds` 数组，靠 `tag` 字符串互相引用 | 机场节点改名、或过滤正则写法（YAML 正则 vs JSON 过滤）不一致导致空组报错 |
| **分流规则格式** | 内联文本规则或 `rule-providers`（YAML/`mrs`） | `route.rules` 搭配外部下载或本地预编译 `.srs`（`rule_set`） | Clash 里的 `classical` 混合规则无法简单一一映射到 sing-box |
| **DNS 与 Fake-IP** | 内置 `dns` 段落独立描述 `nameserver` 与 `enhanced-mode` | `dns.servers` + `dns.rules` + `dns.fakeip` 精细路由，且需在 `route` 配合 `hijack-dns` 动作 | 旧版教程照搬转换后常因新版 sing-box 弃用旧 DNS 字段而启动失败 |

为了直观理解差异，下面是一段典型原生 sing-box 1.11+ 结构的简化配置骨架（仅演示 `outbounds`、`route` 与 `dns` 三个核心区块的串联关系，实际运行需补全完整的入站与节点凭据）：

```json
{
  "dns": {
    "servers": [
      { "tag": "dns_proxy", "address": "https://1.1.1.1/dns-query", "detour": "select_proxy" },
      { "tag": "dns_direct", "address": "https://223.5.5.5/dns-query", "detour": "direct_out" }
    ],
    "rules": [
      { "outbound": "any", "server": "dns_direct" },
      { "rule_set": "geosite-cn", "server": "dns_direct" }
    ],
    "final": "dns_proxy"
  },
  "inbounds": [
    {
      "type": "tun",
      "tag": "tun-in",
      "address": ["172.18.0.1/30"],
      "auto_route": true,
      "strict_route": true
    }
  ],
  "outbounds": [
    {
      "type": "selector",
      "tag": "select_proxy",
      "outbounds": ["auto_best", "node_jp_01", "node_sg_01"]
    },
    {
      "type": "urltest",
      "tag": "auto_best",
      "outbounds": ["node_jp_01", "node_sg_01"]
    },
    { "type": "direct", "tag": "direct_out" }
  ],
  "route": {
    "rules": [
      { "action": "sniff" },
      { "protocol": "dns", "action": "hijack-dns" },
      { "ip_is_private": true, "outbound": "direct_out" },
      { "rule_set": ["geosite-cn", "geoip-cn"], "outbound": "direct_out" }
    ],
    "rule_set": [
      {
        "tag": "geosite-cn",
        "type": "remote",
        "format": "binary",
        "url": "https://example.invalid/geosite-cn.srs",
        "download_detour": "select_proxy"
      }
    ],
    "final": "select_proxy",
    "auto_detect_interface": true
  }
}
```

### 2. 当机场只给 Clash YAML 时，两条务实路径怎么选？

面对不支持原生 sing-box 下发的开放订阅机场，你在实际工程上有两条截然不同的解决路径：

#### 路径 A（推荐给 90% 用户）：直接选用内置格式转换器的客户端
与其自己维护一套随时可能因上游版本升级而报错的 JSON 模板，不如直接使用 **Hiddify**、**Karing**，或在桌面端用 **v2rayN**（切换 sing-box 内核）、在软路由用 **PassWall2**。它们相当于把「订阅解析 + 模板拼装 + 规则集更新」全部封装在了本地客户端内部：
- 当机场新增或下线某个节点时，你只需在软件里点一次「更新订阅」，客户端自动拉取最新机场节点并重生成内存中的 sing-box 运行配置，完全不需要重新去转换生成整份 JSON。
- 在需要为 ChatGPT、Claude、Gemini 或 YouTube 单独固定分流地区（如避开香港节点在 ChatGPT 常见的 `仅 APP(HK)` 限制、或避开部分送中节点）时，Karing 与 v2rayN 均允许直接通过图形界面调整路由规则，无需手写 JSON 数组。
- 在桌面与移动端权限管理方面，Hiddify 与 Karing 的系统代理与虚拟网卡切换界面也更为直观，能够自动处理一部分局域网绕过段与系统代理清理，降低新手误操作造成本地彻底断网的概率。

#### 路径 B（面向极客与原生 SFI/SFA/SFM 用户）：本地可信转换与版本避坑
如果你由于极度看重内存精简、Apple TV 原生兼容或专业网络调试，坚持要使用官方原生 `SFI`/`SFA`/`SFM`，那么解决订阅来源只有三种合规且安全的方式：
1. **优先核对机场面板参数**：登录支持通用订阅的机场用户中心，查看是否有隐藏的或单独列出的 `sing-box` 订阅复制按钮；部分使用现代开源面板的机场本身就已经支持直接输出合乎规范的 sing-box JSON。
2. **绝不把订阅链接贴入陌生第三方在线转换网站**：这是保护账号安全的底线！互联网上搜到的大量「免费万能订阅转换网页」运行在陌生人的服务器上，一旦你把含私人鉴权 Token 的机场订阅 URL 填进去，对方后端不仅能看到你的完整节点服务器地址，还能直接盗用你的账号流量配额，甚至在转换结果里悄悄掺入恶意分流路由。
3. **采用本地运行开源转换器或纯客户端内置工具生成**：如果确实需要把一份 Clash YAML 或 Base64 节点列表转化为原生 JSON，应当在自己本机的安全环境中运行可审查的开源转换工具（例如本地部署的转换服务或开源脚本），将节点字段提取并填进一份经过验证的本地 JSON 模板里，随后通过本地局域网或加密文件传输导入手机端 `SFI`。

### 3. 手动转换或排查时的四大常见字段映射坑点

当你使用本地开源转换工具把机场的 Clash YAML 转换为 sing-box JSON 时，如果发现部分节点消失、测速报错或规则不生效，通常源于以下四处核心字段映射差异：

1. **传输协议与底层握手参数映射错位**：例如在支持三协议的 [一翻云](/brands/yifan/) 或同时包含 `Vless` 与 `AnyTLS` 快照的 [光速云](/brands/guangsuyun/) 订阅中，`VLESS-Reality` 在 YAML 中以 `reality-opts` 配合 `public-key`、`short-id` 表达，而在 sing-box JSON 的 `outbounds` 中必须置于 `tls.reality` 嵌套对象内；`Hysteria 2` 的上下行带宽限速字段（`up` / `down`）与混淆密码字段命名也与 Clash 存在细微出入。较旧版本的转换脚本往往会漏掉 `flow`（如 `xtls-rprx-vision`）或无法识别 `AnyTLS`，导致转换出来的节点连不上网。
2. **策略组过滤正则表达式差异**：很多机场后台依靠节点名称关键词（如匹配「香港」「日本」「新加坡」「美国」）来自动生成分组。Clash YAML 支持的传统正则写法与 sing-box 早期配置或部分第三方转换模板中的正则引擎略有差异，一旦正则未匹配成功，对应 `selector` 或 `urltest` 出站的 `outbounds` 数组就会变成空列表，导致内核直接拒绝启动并抛出配置校验错误。
3. **DNS 策略与 `Fake-IP` 过滤遗漏**：如果转换后的 JSON 开启了 `dns.fakeip` 虚拟地址分配，但忘记把局域网保留域名、系统联网探测域名以及时间同步服务器域名列入直连 DNS 规则，桌面电脑开启 TUN 虚拟网卡后很可能会出现任务栏网络图标误报断网，或者微信扫码、企业内网与开发容器连接异常。对同时运行 WSL2 或 Docker 的开发者，推荐同步阅读 [系统代理与 TUN 虚拟网卡、DNS 回退指南](/guides/articles/tun-vs-system-proxy-dns/) 进行规则校验。
4. **多平台安装包架构与官方源安全核验**：无论选择官方 `SFA`/`SFI`/`SFM` 还是 `Hiddify`、`Karing`、`v2rayN`，都要牢记站内 `PROXY_CLIENTS` 台账中所有客户端的外部官方地址均标注为待联网核实，切勿点击搜索引擎竞价推广里的所谓「中文官网」下载链接。macOS 桌面端须区分 Apple Silicon（`arm64`）与 Intel（`x64`），Windows 端核对 `x64` 与 `ARM64` 架构并检查安装包哈希，Android 端首选 `arm64-v8a` 并核对官方发布者签名，iOS 端只允许在 App Store 内切换个人专属外区账号下载，严禁在手机系统设置的 iCloud 中登录任何陌生共享账号。

## 四、sing-box 生态常见配置排错与实战验证

无论你走的是官方原生 `SFI`/`SFA`/`SFM` 还是 `Hiddify`/`Karing`/`v2rayN`，在使用 sing-box 核心时遇到以下四类高频故障，都可以通过对应逻辑快速排查：

### 1. 导入转换配置后报 `unknown field` 或 `deprecated` 启动失败
sing-box 内核迭代节奏非常快，从 1.8、1.10 演进到 1.11 及以上版本时，逐步淘汰了一批旧版书写方式（例如旧版直接在 `route.rules` 中写 `inbound: "dns-in"` 拦截 DNS 与独立全局 `sniff` 布尔开关，在新版中统一迁移为 `action: "sniff"` 与 `action: "hijack-dns"`；同时旧版内置 `.db` 地理库已被远程或本地 `.srs` 二进制 `rule_set` 全面取代）。如果你从网上复制了一年前的转换模板放进最新版 `SFI`/`SFA` 报错，往往就是因为模板里的 JSON 字段已经被新内核弃用。此时应使用同步更新的客户端（Karing/Hiddify）自带模板，或对照官方文档更新 `route` 动作语法。

### 2. 启用官方端后国内软件直连反而报错，或规则集下载卡死
仔细观察上面配置示例中的 `download_detour` 字段：当原生 sing-box 首次启动并需要去下载远程 `.srs` 分流规则集（或某些地区规则包）时，如果它试图直连某个被干扰的托管源，规则集下载会一直超时卡住，导致国内分流规则压根没有生效；反之若把 `download_detour` 指向了尚未连通的无效出站，也会陷入死锁。因此首次配置时务必确保测试节点可用且规则集镜像源可正常拉取。

### 3. 节点全部显示延迟超时（Timeout）
当确认节点本身并未过期且机场面板工作正常时，在 sing-box 体系下最常见原因有两个：
- **本地系统时间偏差**：包括 `VLESS-Reality`、`Trojan` 与 `Hysteria 2` 在内的现代 TLS/QUIC 协议高度依赖精准时间戳校验，手机或电脑时间偏差数十秒就会握手失败。请先核对系统自动同步时间，详见 [节点超时与时间漂移排查](/guides/articles/time-drift-timeout-troubleshooting/)。
- **机场不支持第三方通用订阅**：再次确认你所使用的机场不属于 [飞猫云](/brands/feimao/)、[隐形人](/brands/yinxingren/)、[SOGO 云](/brands/sogo/) 等仅限官方专属客户端的封闭品牌（详参 [专属客户端 vs 通用订阅对比](/compare/dedicated-client-vs-universal-sub/)）。

### 4. 如何理性在 `sing-box` 与 `Mihomo` 两大生态之间做最终抉择？
在 2026 年的代理工具选型中，两者根本不存在「谁完全碾压谁」的绝对高下，真正理性的取舍标准非常朴素：
- 如果你主要在 **Windows / macOS / OpenWrt 软路由** 上使用，希望完美承接绝大多数机场直接下发的标准 **Clash YAML**，重度依赖类似 `Clash Verge Rev` 的前置脚本覆写或 `OpenClash` / `Nikki`（注意 `Nikki` 严格要求 `OpenWrt` 24.10 及以上版本，旧版固件不兼容）图形化规则管理，选择 **[Mihomo 生态](/clients/mihomo/)** 摩擦最低、生态最成熟。
- 如果你追求 **更低的内存与电量开销**（尤其老旧手机、iOS 严苛内存限制或低配置终端）、希望跨五端统一界面且不想处理复杂 YAML 缩进，或者你本身在用 **Karing / Hiddify / HomeProxy（OpenWrt fw4）** 以及需要用 **v2rayN** 自由切换多核心，那么 **[sing-box 生态](/clients/sing-box/)** 就是最契合现代底层架构的理想选择。
- **OpenWrt 软路由的 sing-box 选型补充边界**：在软路由侧部署 `HomeProxy` 或 `PassWall2` 前，同样必须在 SSH 终端核对固件版本号、CPU 架构（`x86_64`、`aarch64` 或其他指令集）、剩余闪存空间以及防火墙后端。若固件本身较老仍使用传统架构或低闪存空间紧张，切忌硬装过重插件；单台路由器在同一时刻也只能开启一个透明代理管理插件，不可将 `HomeProxy`、`PassWall2` 与 `OpenClash` 或 `Nikki` 同时启用。
- **跨平台长期运维与数据保护**：无论最终选定 `SFI`、`SFA`、`SFM` 还是 `Karing`、`Hiddify`、`v2rayN`，都要坚持三项安全底线：第一，官方来源地址核实前绝不点击来源不明的网盘或竞价推广安装包，下载后校验 SHA-256 哈希或发布者签名；第二，除非需要让客厅电视或同局域网设备共享代理，否则关闭「允许局域网连接」避免在公共无线网络下暴露本地端口；第三，妥善保管含私人认证令牌的机场订阅链接，不随意贴入公共在线转换站，并结合 [AI 与流媒体 GeoIP 分流实战](/guides/articles/ai-streaming-geoip-routing/) 隔离固定地区出口节点，保障生产工具与账号长期稳定运行。
